#### UC-NOTICE-01-B ｜ 标题长度与正文大载荷边界

| 字段 | 内容 |
| --- | --- |
| **优先级** | P2 |
| **场景类型** | 边界条件 |
| **测试维度** | 功能, 性能 |
| **关联任务** | TC-NOTICE-01 |
| **关联接口** | `POST /notice` |

**前置条件**

1. 见 3.2 通用前置条件
2. 已用 `D-ADMIN` 取得令牌
3. 已核对约束：`noticeTitle @NotBlank @Size(max=200)`、`content @NotBlank`（**无长度上限**，`content` 列为 `LONGTEXT`）、`noticeType @NotNull`、`noticeLevel @NotNull`、`publishScope @NotNull`
4. 已准备一个约 **100 KB** 的正文文本文件（含中文与换行）

**测试步骤**

1. `noticeTitle` = 200 字符（边界值），其余字段合法 → 提交
2. `noticeTitle` = 201 字符 → 提交
3. `noticeTitle` = `""`，再试 `"   "`（全空格）→ 提交
4. `content` = 100 KB 长文本（用脚本生成 JSON，避免手工粘贴）→ 提交，记录响应耗时
5. 查询步骤 4 记录落库的 `content` 长度，并与原始文本长度比对
6. `content` = `"   "`（全空格）→ 提交

**预期结果**

1. 步骤 1：`code = 200`（标题边界 200 通过）
2. 步骤 2：`code = 400`，提示「公告标题长度不能超过 200」
3. 步骤 3：两次均 `code = 400`，提示「公告标题不能为空」（`@NotBlank` 对全空格生效）
4. 步骤 4：`code = 200`，响应耗时在基线内（记录实测值，建议 < 2000 ms）；**不得**出现 HTTP 413 或 `code = 5000`
5. 步骤 5：`SELECT CHAR_LENGTH(content) FROM oa_notice WHERE id = <id>;` 与原始字符数**完全相等**（无截断、无转义膨胀）；`LONGTEXT` 上限远大于 100 KB
6. 步骤 6：`code = 400`，提示「公告内容不能为空」——`@NotBlank` 对全空格生效，**不得**落库空白正文
7. 边界 200/201 行为**明确分界**；所有失败提交均不落库

**数据校验**

```sql
SELECT id, CHAR_LENGTH(notice_title) AS title_len, CHAR_LENGTH(content) AS content_len,
       OCTET_LENGTH(content) AS content_bytes
FROM oa_notice WHERE notice_title LIKE 'T长度%';
-- 预期：不存在 title_len=201 的行
```

**前置条件**

3. 已构造 3 条公告：① 草稿（`status=0`）② 已发布（`status=1`）③ 已下架（`status=2`）
4. 已对②执行过至少 1 次用户端详情读取（使 `readCount = 1` 或以上）

**测试步骤**

2. 逐条读取响应字段名，列出全部键
3. 检查响应中是否存在 `content` 键；检查 `publisherName`、`readCount`
4. 用 `curl -w '%{size_download}'`（配合 `--noproxy '*'`）记录本次响应的**字节数**

**预期结果**

2. `records` 中 `noticeStatus` 覆盖 `0`、`1`、`2`（**管理端不过滤状态**）

4. **`records` 中不存在 `content` 字段**（`NoticeVO` 刻意不含正文）→ 性能/安全双重要求：`content` 为 `longtext`，列表带上会让分页传输量翻几十倍
5. `publisherName` 非空且等于发布人 `realName`（为空时回退 `username`）；`readCount` 为数字（已发布的那条 ≥ 1，未读的为 0）
6. 排序为 `top_flag DESC, id DESC`（置顶项在最前，其余按 id 倒序）
7. 步骤 4 的响应字节数应远小于步骤 5（详情含正文时更明显）→ 记录两个数值作为性能基线
8. 若 `records` 中出现 `content` → **P1 缺陷**（列表泄漏正文且传输量放大）

**数据校验**

```sql
SELECT n.id, n.notice_status, n.view_count,
       (SELECT COUNT(*) FROM oa_notice_read r WHERE r.notice_id = n.id) AS read_count,
       n.publisher_id
FROM oa_notice n WHERE n.is_deleted = 0 ORDER BY n.top_flag DESC, n.id DESC;
-- 预期：与响应 records 逐条一致（read_count 相等）
```
