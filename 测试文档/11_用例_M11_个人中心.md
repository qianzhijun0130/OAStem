> 模块范围：个人信息查询、资料修改、头像更换与路径白名单、修改密码、密码安全与日志脱敏、越权防护（接口不接收 userId）、未登录访问、页面交互

## 模块信息

| 项 | 内容 |
| --- | --- |
| **对应接口** | `GET /profile/info`、`PUT /profile/update`、`PUT /profile/avatar`、`PUT /profile/password` |
| **对应页面** | `/profile`（个人中心，静态路由，`views/profile/index.vue`） |
| **权限码** | **无**（四个接口均不挂权限码，仅要求登录态；只要登录成功即应能维护自己的资料） |
| **关键设计约束** | 所有接口以 `SecurityContextUtil.getCurrentUserId()` 为**唯一操作对象**，**接口不接收 `userId` 参数**；头像仅接受 `/uploads/` 前缀的内部路径（`file.access-prefix` 默认 `/uploads`） |
| **关键校验规则** | `nickname` `@Size(max=50)`；`mobile` `@Pattern(^$\|^1[3-9]\d{9}$)`；`email` `@Email` + `@Size(max=100)`；`newPassword` `@NotBlank` + `@Size(min=6,max=20)`；`oldPassword` `@NotBlank` |
| **日志约束** | `PUT /profile/password` 标注 `@OperationLog(saveParams=false)`；`PUT /profile/update` 标注 `@OperationLog(saveParams=true)`；`PUT /profile/avatar` **未**标注操作日志 |
| **返回结构** | `ProfileVO`：`id`、`username`、`realName`、`nickname`、`avatar`、`gender`、`mobile`、`email`、`workNumber`、`position`、`entryDate`、`deptId`、`deptName`、`roles`、`lastLoginTime`、`lastLoginIp` |
| **依赖模块** | M12 文件存储（头像上传来源与 `/uploads/**` 静态映射）、M01 登录与认证（改密后的登录验证）、M14 操作日志（改密日志脱敏校验） |

### 本模块执行前置（在 3.2 通用前置之外）

1. 已准备两个账号：`admin`（id=1）与测试账号 `t_profile_b`（属 `D-DEPT-A`，具 `super_admin` 之外的普通角色，**无任何 `file:*` / `profile:*` 权限码**），两者密码均已知。
2. 已按 7.1.1 **备份 admin 密码哈希**；本模块 `TC-PROFILE-07` / `08` / `09` 会真实改密，**测试结束必须逐字符还原**。
3. 已取得两个身份的 JWT 令牌；改密后须用新密码重新登录取新令牌（3.4-4 令牌滞后）。
4. 已确认 `file.access-prefix` = `/uploads`（见 `application.properties`），且 `/uploads/**` 在安全配置中属 `permitAll`（静态图片映射，用于头像公开展示）。
5. 已理解 `ProfileUpdateRequest` 只含 4 个可自助字段（`nickname` / `gender` / `mobile` / `email`），姓名、工号、部门、岗位、入职时间属人事档案、由管理员维护。
6. 个人中心为**静态路由**，不在菜单树中；验证「无权限码账号仍可进入」时以 3.4-4「权限两个数据源」为判定基准。

#### UC-PROFILE-02-N ｜ 查询接口携带他人 userId 参数被忽略

| 字段 | 内容 |
| --- | --- |
| **优先级** | P0 |
| **场景类型** | 正常场景 |
| **测试维度** | 安全 |
| **关联任务** | TC-PROFILE-02 |
| **关联接口** | `GET /profile/info` |

**前置条件**

1. 见 3.2 通用前置条件
2. `t_profile_b` 已按 7.1 创建（记其 id 为 `B_ID`），资料与 admin 明显不同（不同 `realName`、`nickname`）
3. 已取得 `t_profile_b` 的 token

**测试步骤**

1. 用 `t_profile_b` token 发送 `GET /profile/info?userId=1`
2. 再发送 `GET /profile/info?id=B_ID` 与 `GET /profile/info?user_id=1`
3. 记录每次返回的 `data.id` 与 `data.username`

**预期结果**

1. 三次均 `code = 200`
2. 三次 `data.id` 均等于 `t_profile_b` 的 id（`B_ID`），**不等于** `1`
3. 三次 `data.username` 均为 `t_profile_b` 的用户名
4. 结论：`userId` 查询参数被服务端忽略——接口签名中不含该参数，操作对象唯一取自 `SecurityContextUtil.getCurrentUserId()`
