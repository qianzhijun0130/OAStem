### 2.3 环境注意事项（执行前必读）

| 序号 | 事项 | 影响与处置 |
| --- | --- | --- |
| 1 | 终端注入了 `SERVER__PORT` 环境变量 | 会被松散绑定覆盖 `server.port`，起服务必须加 `--server.port=8080` |
| 2 | 终端注入了 `HTTP_PROXY` / `HTTPS_PROXY` | 用 curl 访问本机必须加 `--noproxy '*'`，否则报 502 而非连接失败，易误判 |
| 3 | 后端日志在 Windows 下为 GBK | 用 `grep` 查中文日志会报 `Binary file matches`，需 `iconv -f GBK -t UTF-8` |
| 4 | **权限存在两个数据源** | `/auth/menus` 实时查库；接口鉴权读 JWT 的 `perms`（8 小时不刷新）。**改了菜单权限必须重新登录**，否则出现「侧边栏有菜单、点进去 403」——这是令牌滞后，不是权限数据错误 |
| 5 | JWT 为无状态令牌 | 退出登录 / 禁用账号后，**旧令牌在有效期内仍可用**。此为已知设计行为，测试时按"已知项"记录，不判为缺陷 |
| 6 | `oa_department.leader_id` 当前全为 NULL | 流程中使用「部门主管」审批规则的节点会**解析不出候选人**，表现为「流程在跑但待办为空」。测 M09 前须先设置部门负责人 |
| 7 | `vite build` 清空 `dist/` 可能被 IDE 沙箱批量删除守卫拦截 | 属环境限制，先手工删除 `dist/` 目录再构建 |

## 三、任务编号与优先级规则

### 3.1 编号规则

`TC-<模块代码>-<两位序号>`，例如 `TC-LOGIN-03`、`TC-NOTICE-11`。

模块代码：`LOGIN` / `USER` / `ROLE` / `DEPT` / `MENU` / `DICT` / `NOTICE` / `FLOW` / `APPROVAL` / `DASH` / `PROFILE` / `FILE` / `LLOG` / `OLOG`，横切用 `X01`~`X07`。

### 3.2 优先级定义

| 级别 | 含义 | 执行要求 |
| --- | --- | --- |
| **P0** | 主链路冒烟；失败则系统不可用 | **必须全部通过**才允许继续后续测试 |
| **P1** | 核心功能与关键约束（含权限、越权） | 必须执行，失败须修复后复测 |
| **P2** | 重要功能与常见异常分支 | 必须执行 |
| **P3** | 边界、体验、极端场景 | 建议执行，时间不足可延后 |

### 3.3 判定标准

- **通过**：实际结果与「预期结果」完全一致（含业务错误码、提示文案、状态码）。
- **阻塞**：前置任务未通过或环境不可用，无法执行，须标注并上报。
- **失败**：实际结果与预期不符，提缺陷单。
- 接口类任务以**业务错误码**（如 `2405`）为准，不以 HTTP 状态码为准。本系统的响应约定（2026-09-29 实测确认）：
  - 业务成功与**鉴权失败**均返回 **HTTP 200 + 业务码 + 统一 `Result` 包装**（如 `@PreAuthorize` 拒绝 → HTTP 200 + `code=403`）；
  - 仅**认证失败**（缺令牌 / 令牌非法或过期）由安全过滤链直接写出 **HTTP 401 + `code=401`**，不使用 `Result` 包装；
  - 因此判定一律以 `code` 为准，且需注意 `401` 与 `403` 的 HTTP 状态码并不同源。

### 8.2 清理要求（硬性）

1. **测试数据必须可清理**：新增的账号、角色、部门、菜单、字典项、公告、审批实例、上传文件，测试结束前全部清理或逻辑删除。

3. **物理文件同步清理**：删除 `oa_file` 记录时，须同步删除 `storage/files` 下对应物理文件。
4. **清理前先备份**：批量删除前先导出相关表数据留档，便于回溯。
5. **权限类变更需复核**：测试中若改动过菜单/角色权限，清理后必须**逐项复核回基线**（`oa_menu` 62 条、超管授权完整）。
6. **清理后重新登录验证**：清理完成后用超管重新登录，确认侧边栏与页面正常。
