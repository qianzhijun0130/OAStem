| **对应页面** | `/workflow/apply`（发起申请）、`/workflow/todo`（我的待办）、`/workflow/done`（我的已办）、`/workflow/mine`（我的发起）、审批详情抽屉（`views/workflow/components/ApprovalDetailDrawer.vue`） |

### 本模块执行前置（在 3.2 通用前置之外）

1. **PRE-M09-1** 已为参与「部门主管」规则的测试部门设置负责人：`UPDATE oa_department SET leader_id=<测试账号id> WHERE id=<测试部门id>;`，否则该规则节点解析出的候选人为空（3.4-6），表现为「流程在跑但没人能审批」。**测后必须还原为 NULL**。
2. **PRE-M09-2** 已按 7.1 准备 `D-FLOW-2LVL`：**两级审批模板，两级均用「指定人员」规则**（明确 id，不使用部门主管规则），命名为 `t_appr_2lvl`，已部署、`status=1`。另准备 `D-FLOW-1LVL`（单节点，`t_appr_1lvl`）用于边界用例。
3. **PRE-M09-3** 已准备 5 类身份令牌：`D-ADMIN`（全部权限码）、申请人 A（`system:approval:start`/`:mine`/`:query`）、审批人 B 与 C（`system:approval:todo`/`:done`/`:complete`/`:transfer`/`:query`）、无关账号 D（仅 `:query`，非任何节点候选人、非发起人、非历史处理人）、账号 G（**无任何 `system:approval:*` 权限码**）。
4. **PRE-M09-4** 涉及清理 Flowable 运行时 / 历史表的用例（`UC-APPROVAL-04-E`、`UC-APPROVAL-16-B`、`UC-APPROVAL-23-*`）须先 `SET FOREIGN_KEY_CHECKS=0`，或**按子表顺序删除**：`act_ru_variable` → `act_ru_identitylink` → `act_ru_task` → `act_ru_execution`；历史侧同理 `act_hi_*`。`oa_approval_record` 与运行时表存在外键约束，**不得**先删主表。
5. **PRE-M09-5** 审批人为「候选人」语义：同一任务挂多个候选人时，**任一候选人处理即完成**，其余人的待办随即消失。用例中的「待办出现 / 消失」判定均以此为前提。
6. **PRE-M09-6** 已确认 `oa_approval_instance` / `oa_approval_record` 基线为空（或已记录基线条数），便于以「增量」作可判定断言。

5. 步骤 3：`data.records` 首条 `id` = 步骤 2 的实例 id，`status = 2`、`statusName = 审批中`、`applicantId` = A 的 id
6. 流程变量含 `formData` / `applicantId` / `title` 三项
7. 响应体不含堆栈、不含其他用户的申请

**数据校验**

```sql
SELECT id, flow_def_id, flow_code, title, applicant_id, proc_inst_id, form_data, status, current_node
FROM oa_approval_instance WHERE id = <实例id>;

SELECT id, instance_id, task_id, node_id, node_name, handler_id, action, opinion
FROM oa_approval_record WHERE instance_id = <实例id>;

SELECT ID_, PROC_INST_ID_, PROC_DEF_ID_, BUSINESS_KEY_ FROM ACT_RU_EXECUTION WHERE BUSINESS_KEY_ = '<实例id>';
SELECT ID_, PROC_INST_ID_, TASK_DEF_KEY_, NAME_, ASSIGNEE_ FROM ACT_RU_TASK WHERE PROC_INST_ID_ = '<procInstId>';
-- 预期：BUSINESS_KEY_ = 审批单 id；ASSIGNEE_ 为 NULL
```

**测试步骤**

1. 用同一 body 在 200 ms 内并发发起 **5 次**相同请求
2. 统计 `code = 200` 的次数与返回的实例 id 集合
3. 查询 `oa_approval_instance` 条数 N1，并按 `BUSINESS_KEY_` 分组统计 `ACT_RU_EXECUTION`
4. 检查是否出现「同一业务 key 挂多个流程实例」或数据错乱

**预期结果**

1. 5 次请求均返回 HTTP `200`（业务码 `200` 或 `5000`），**无连接被拒 / 超时**
2. 若接口无幂等控制则 `N1 - N0 ∈ {1..5}`，且每个实例各自对应 1 条 `ACT_RU_EXECUTION`（`BUSINESS_KEY_` 唯一）

4. **不得**出现表结构类异常（如唯一键冲突导致事务半提交）
5. 结论：记录实际并发行为；若产生多条独立申请，登记为「无幂等控制（待确认）」而非缺陷，除非出现数据错乱

**数据校验**

```sql

SELECT BUSINESS_KEY_, COUNT(*) c FROM ACT_RU_EXECUTION GROUP BY BUSINESS_KEY_ HAVING c > 1;
-- 预期：0 行（每个审批单最多挂 1 个运行实例）
```
