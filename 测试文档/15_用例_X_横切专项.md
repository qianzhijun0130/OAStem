### 横切专项通用前置（在总纲 3.2 之外补充）

1. **性能类**：需先完成 7.1 测试数据工厂的数据放大准备（用户 ≥ 200、操作日志 ≥ 1000、公告 ≥ 200），并在执行前后**记录基线数据量**，否则耗时对比无意义。
2. **安全类**：涉及越权的用例必须**同时准备两个不同归属的身份**（身份 A 与身份 B，分属不同部门 / 不同角色），且各自持有有效令牌；令牌必须来自**最近一次登录**（见总纲 3.4-4）。
3. **兼容性类**：浏览器使用 Chrome（主）、Edge（次）、Firefox（辅）最新稳定版；分辨率以浏览器窗口 `innerWidth` 实测为准，不得用显示器物理分辨率替代。
4. **回归类**：回归用例默认引用 M01~M14 各模块的同名主链路数据，**不得另造平行数据**，避免判定基准漂移。
5. **通用环境事实**：本机 curl 必须 `--noproxy '*'`；后端必须 `--server.port=8080` 启动；Windows 下后端日志为 GBK，检索需 `iconv -f GBK -t UTF-8`。

# 专项一 性能测试

## 专项说明

| 项 | 内容 |
| --- | --- |
| **专项目标** | 验证系统在**正常载荷**与**异常大载荷**下的响应时间、内存占用、载荷体积与并发正确性，确保不会因单次请求拖垮服务 |
| **判定基线** | ① 普通列表 / 详情接口 **< 1s**；② `GET /dashboard/overview` 聚合接口 **< 2s**；③ 列表接口 `pageSize` 有硬上限且不一次查出全表；④ 导出走流式写入（SXSSF），JVM 堆内存平稳（无 OOM）；⑤ 并发场景下数据无丢失、无相互覆盖 |
| **量化口径** | 响应时间取 `curl -w '%{time_total}'` 的 **5 次连续调用中位数**（排除首次 JIT 预热值），单位秒，保留 3 位小数 |
| **执行前置** | 见总纲 3.2 + 本文件「横切专项通用前置」第 1 条；后端日志已重定向至 `F:/tmp/oa_test_backend.log`；已确认 `SERVER__PORT` 被显式覆盖为 8080 |
| **不判缺陷的情形** | 首次冷启动请求耗时偏高（JIT / 连接池预热）；本机 CPU 满载时耗时抖动（须在记录中注明环境噪声） |

# 专项二 安全测试

## 专项说明

| 项 | 内容 |
| --- | --- |
| **专项目标** | 验证鉴权与越权防线、注入与 XSS 防护、敏感信息不泄漏、文件上传安全、审计覆盖与密钥外置，确认不存在「权限码漏挂」「水平/垂直越权」「注入生效」三类高危问题 |
| **判定基线** | ① **无令牌** → **HTTP 401 + `code=401`**（无 `Result` 包装）；② **有令牌但无权限码** → **HTTP 200 + `code=403`**；③ **有令牌且有权限码** → `code=200`；④ 注入载荷不改变查询语义；⑤ 脚本内容回显被转义或过滤，**不执行**；⑥ 响应 / 日志 / 导出文件均无密码原文、密码哈希、令牌明文；⑦ 文件按白名单校验**真实类型或扩展名**，文件名被安全处理 |
| **执行前置** | 见总纲 3.2 + 本文件「横切专项通用前置」第 2 条；**必须准备两套相互隔离的身份 A / B**（不同部门、不同角色），并各自持有**最近一次登录**签发的令牌 |
| **高危判定** | 越权放行、注入生效、认证绕过 → **P0 缺陷**；权限码失效、敏感信息泄漏 → **P1 缺陷** |
| **已知不判缺陷** | `logout` 后旧令牌仍可用、禁用账号旧令牌仍可用（JWT 无状态，总纲 3.4-5）；改权限后不重新登录仍按旧 `perms` 判定（令牌滞后，总纲 3.4-4） |

### SMOKE-D01 修复实施记录（2026-09-30）

**根因重审**：冒烟 14 失败表层是「hrAudit（`role:4`）待办为 0」；深层是 `assignCurrentTasks#resolveCandidates` 在 `ASSIGNEE_ROLE` 分支查 `oa_user_role` 时**角色下无用户** → 不追加任何 candidate user，仅 Flowable 部署时写入的 `group=role:4` 身份链接；待办 `taskCandidateUser` 不解析候选组，故无人可见。本库无 Flowable IDM（无 `ACT_ID_*` 表）也无法依赖框架兜底。

**修复方案**：按文档建议方案 A——运行期把角色下所有用户 `addCandidateUser`；同时**角色下无用户时回退到 SUPER_ADMIN**（`oa_role.role_code='SUPER_ADMIN'` 下所有用户）。业务约定：超管可处理所有审批任务，避免节点无人处理导致单据卡死（与内置 leave/expense 的二节点 demo 流程默认测试场景一致）。

**代码改动（2 个文件）**：

1. `BpmnXmlNormalizer#preExpandCandidateUsers`（新增）：部署期 DOM 改写，每个 `<userTask>` 收集 `flowable:candidateGroups="role:X"` 与 `<oa:assignee type="role" value="X">`，通过 `userRoleMapper` 查角色下用户 id，**追加**到 `flowable:candidateUsers`（与已有值合并去重、不删除原 `candidateGroups`）。角色下无用户时**跳过**（保留原属性，由运行期兜底）。
2. `FlowDefinitionServiceImpl#deployAndBind`：在 `overrideProcessId` 后调 `preExpandCandidateUsers(normalizedXml, this::resolveRoleUsers)`。**覆盖 import/bootstrap/编辑全路径**。
3. `ApprovalServiceImpl#resolveCandidates` ASSIGNEE_ROLE 分支：查角色下用户为空时**回退查 `oa_user_role WHERE role_id=1`（SUPER_ADMIN）**；兜底为空才告警「任务将无人处理」。新增常量 `SUPER_ADMIN_ROLE_ID = 1L`。
