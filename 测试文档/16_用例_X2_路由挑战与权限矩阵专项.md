### 专项通用前置（在总纲 3.2 之外补充）

1. **服务形态**：后端 `http://127.0.0.1:8080`、前端 `http://127.0.0.1:3000` 同时运行；后端启动命令必须显式带 `--server.port=8080`（本机 `SERVER__PORT` 环境变量会覆盖配置）。
2. **浏览器要求**：路由挑战类用例**必须用真实浏览器**执行（Playwright 驱动系统 Edge），不得只靠 `curl` —— 路由守卫、重定向、`history` 行为都发生在浏览器侧。
3. **curl 约定**：访问本机端口一律加 `--noproxy '*'`（本机注入了 `HTTP_PROXY`，不加会走代理并表现为 502）。
4. **令牌来源**：所有令牌必须来自**最近一次真实登录**（`POST /auth/login`），不得用历史脚本伪造 —— 本项目 JWT 为 **HS384**（密钥长度决定），历史脚本按 HS256 产出的令牌会被服务端直接拒绝。
5. **测试账号**：专项六需要 6 个测试账号 + 2 个测试角色（见 7.1 与 `TC-X09-01`）。**执行前必须先完成本文件 7.1 的建号步骤**，否则专项六全部用例无法执行。
6. **数据处置**：测试账号与角色属**新增数据**，测后必须按 `TC-X09-08` 清理回基线（`user_cnt=1`、`role_cnt=5`、`user_role_cnt=1`）。
7. **已知行为不判缺陷**：① 后端 `oa_role.data_scope` 字段**前端可设、后端只存不用**（全仓无任何查询按它过滤）—— 属「功能未实现」，按 P2 登记而非环境问题；② 权限变更后旧令牌不刷新（`perms` 固化在 JWT 内 8 小时），表现为「侧边栏菜单实时变了、接口仍 403」，处置是**重新登录**。

# 专项五 路由挑战测试

## 专项说明

| 项 | 内容 |
| --- | --- |
| **专项目标** | 以**对抗视角**验证前端路由体系在异常输入、恶意输入与状态异常下的行为：守卫是否可绕过、动态路由是否可越权注册、重定向链路是否可被劫持、兜底策略是否泄漏数据 |
| **判定基线** | ① 未认证深链接一律跳登录且**不渲染任何业务骨架**；② `redirect` 参数**只在同源内跳转**（开放重定向为 P0）；③ 非法 / 篡改令牌一律 **HTTP 401**；④ 路径变体不得绕过守卫；⑤ 任何重定向链路**不得死循环**；⑥ **前端 404 不等于安全**，后端必须独立拦住 |
| **核心命题** | 「前端路由守卫是 **UX 层**的第一道闸，不是安全边界」—— 本专项须用 `curl` 绕过前端证明后端独立鉴权有效 |
| **执行方式** | Playwright 驱动真实浏览器（系统 Edge）为主，`curl` 为辅（用于绕过前端做交叉验证） |
| **不判缺陷的情形** | 浏览器自身的 URL 规范化行为（如 `/./a` → `/a`、尾斜杠处理）—— 属规范要求，只记录实际值 |

## TC-X08-02 开放重定向防护 · `P0`

> **场景覆盖**：✅ 正常　✅ 边界　✅ 异常与容错
> **测试维度**：安全
> **关联接口**：页面 `/login`、`route.query.redirect`

> **风险提示（源码核对结论）**：`src/views/login/index.vue` 的 `handleLogin()` 中，跳转目标直接取自 `route.query.redirect`，**未做同源校验**：
> ```ts
> const rawRedirect = route.query.redirect;
> const redirect = typeof rawRedirect === "string" && rawRedirect ? rawRedirect : "/";
> router.push(redirect);
> ```
> 由于 `vue-router` 对**绝对 URL** 与**协议相对 URL** 的处理依赖浏览器行为，存在被利用为**开放重定向（Open Redirect）**的可能。本任务即验证该风险是否成立。

4. `redirect` 参数经 vue-router 规范化：`%2F` 会被还原为 `/`（实测 `?redirect=/system/user` 而非 `?redirect=%2Fsystem%2Fuser`），断言时须以**规范化后**的形态为准。
5. `GET /system/user/{id}` **不存在**（无详情端点）→ 返回 `405`。

### 缺陷

| 编号 | 级别 | 描述 | 关联用例 |
| --- | --- | --- | --- |
| `X2-D01` | **P2** | `oa_role.data_scope`（数据权限范围）**可配置、可落库，但后端无任何查询按它过滤**。实测把角色 `X2_NOTICE_ONLY` 的 `data_scope` 由 `1`（全部数据）改为 `4`（仅本人），同一账号重新登录后查询 `/system/user/page`，返回 **`total=8`**（含 admin 与其他部门的用户），与 `data_scope=1` 时**完全一致** —— 即该字段为**装饰性字段**，配了不生效 | `UC-X09-05-E` |
| `X2-D02` | **P1** | **逻辑删除用户后无法重建同名账号**。`DELETE /system/user/{id}` 只置 `is_deleted=1`、**不改写 `username`**，而唯一索引 `uk_username` 为**单列、不含 `is_deleted`**，故被删行仍占用该用户名。实测：删除 `x2_tech` 后用完全相同的 `username` 重建 → `HTTP 200` + **`{"code":5000,"message":"系统内部错误，请稍后重试"}`**（唯一索引冲突被兜底成 5000，而非可读的业务提示）。对比：字典 / 流程定义表在删除时会把编码改写为 `{code}_deleted_{id}` 释放索引，**用户 / 角色 / 部门三张表未做此处理** | `UC-X09-08-B` |

> **`X2-D02` 的影响面**：员工离职后被删除，其工号 / 账号名**永久不可复用**；且前端只会看到「系统内部错误」，运维需查库才能定位。修复方向有二 —— ① 删除时改写 `username` 为 `{username}_deleted_{id}`（与字典表一致）；② 唯一索引改为 `(username, is_deleted)` 复合索引。按用户流程，**本轮只登记不改代码**。
