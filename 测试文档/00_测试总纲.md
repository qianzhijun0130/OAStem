## 1.2 编制目的

把系统现有功能拆解为**可独立执行、可独立判定、可追溯**的测试用例，使任何一位测试人员无需阅读源码，仅凭文档即可明确：

1. **测什么** —— 模块 → 测试任务 → 测试用例三级分解；
2. **怎么测** —— 每条用例给出编号化测试步骤与所需数据；
3. **测到什么程度** —— 每条用例显式标注场景类型（正常 / 边界 / 异常容错）与测试维度（功能 / 性能 / 安全 / 兼容性 / 回归）；
4. **判什么** —— 预期结果精确到业务错误码、HTTP 状态码、响应字段、落库数据；
5. **为什么测** —— 可追溯到具体接口、菜单权限码与历史缺陷点。

# 第二章 测试用例规范

## 2.1 三级分层模型

```
模块 Module            M01 登录与认证
  └─ 测试任务 Task     TC-LOGIN-01  ← 勾选单位 / 进度单位（沿用 v1.0 编号，进度零迁移）
       ├─ 测试用例 Case UC-LOGIN-01-N  正常场景
       ├─ 测试用例 Case UC-LOGIN-01-B  边界条件
       └─ 测试用例 Case UC-LOGIN-01-E  异常与容错
```

| 层级 | 用途 | 是否可勾选 | 编号前缀 |
| --- | --- | --- | --- |
| **Module 模块** | 业务域划分，对应侧边栏一级入口 | 否 | `M01`~`M14` / `X` |
| **Task 测试任务** | 进度管理与勾选看板的单位，映射一个功能点 | **是** | `TC-` |
| **Case 测试用例** | **原子执行单位**，含四要素，一次执行即得结论 | 否（随 Task 勾选） | `UC-` |

> **勾选规则**：一个 Task 下的**全部 Case 执行完毕且结论明确**后，方可勾选该 Task。若有 Case 失败，仍勾选完成但追加 `⚠️`，并在模块文件「执行记录」中登记缺陷编号。

## 2.2 编号规则

### 2.2.1 测试任务（Task）

```
TC-<模块代码>-<两位序号>
```

模块代码：`LOGIN` / `USER` / `ROLE` / `DEPT` / `MENU` / `DICT` / `NOTICE` / `FLOW` / `APPROVAL` / `DASH` / `PROFILE` / `FILE` / `LLOG` / `OLOG`；横切任务用 `X01`~`X07`。

示例：`TC-LOGIN-03`、`TC-USER-11`、`TC-X02-05`

### 2.2.2 测试用例（Case）

```
UC-<模块代码>-<两位任务号>-<场景字母><可选序号>
```

| 场景字母 | 含义 | 要求 |
| --- | --- | --- |
| `N` | **正常场景**（Happy Path） | 每个 Task **至少 1 条** |
| `B` | **边界条件**（Boundary） | 存在数值 / 长度 / 时间 / 集合边界时必须覆盖 |
| `E` | **异常与容错**（Exception & Fault Tolerance） | 存在外部依赖 / 非法输入 / 并发 / 失败分支时必须覆盖 |

同类型多条时追加序号：`UC-USER-03-B1`、`UC-USER-03-B2`

示例：`UC-LOGIN-01-N`、`UC-LOGIN-07-B1`、`UC-USER-05-E`

### 2.2.3 编号唯一性

- 全部 `TC-` 编号在系统内唯一；全部 `UC-` 编号在系统内唯一。
- 编号**一经分配不得复用**，用例废弃时标记 `[废弃]` 而不回收编号。
- 校验方法（CI 可执行）：

```bash
# 校验 TC- / UC- 编号重复
grep -ohE '\b(TC|UC)-[A-Z0-9]+-[0-9]{2}(-[NBE][0-9]*)?\b' 测试文档/*.md | sort | uniq -d
```

## 2.3 用例标准格式（强制）

每条测试用例**必须**包含以下 8 个字段，字段顺序与名称不得变更：

```markdown
#### UC-XXX-NN-N ｜ 用例标题（一句话，动宾结构）

| 字段 | 内容 |
| --- | --- |
| **优先级** | P0 / P1 / P2 / P3（定义见 2.5） |
| **场景类型** | 正常场景 / 边界条件 / 异常与容错 |
| **测试维度** | 功能 / 性能 / 安全 / 兼容性 / 回归（可多选，逗号分隔） |
| **关联任务** | TC-XXX-NN |
| **关联接口** | `METHOD /path`（前端用例填 `页面 /xxx`） |

**前置条件**

1. …（可用「见 3.2 通用前置条件」引用，只写差异部分）
2. …

**测试步骤**

1. …（每步一个可执行动作，不写"验证xxx"，验证写进预期结果）
2. …

**预期结果**

1. …（可断言的客观事实：业务码 / HTTP 状态 / 字段值 / 落库值 / 页面表现）
2. …

**数据校验**（可选，接口类用例建议填写）

```sql
-- 落库核对 SQL
SELECT ... ;
```

```

### 2.3.1 字段填写要求

| 字段 | 硬性要求 |
| --- | --- |
| **优先级** | 单一值，取自 `P0`~`P3` |
| **场景类型** | 单一值，取自 正常场景 / 边界条件 / 异常与容错 |
| **测试维度** | 至少 1 个；跨维度用例可多选（如「安全, 回归」） |
| **前置条件** | 必须写清**依赖的数据状态**（哪张表需要有什么记录）与**身份**（用哪个账号 / 令牌）。不得写"环境正常"这类空话 |
| **测试步骤** | 必须**编号化**且可机械执行；接口类须给出 method + path + 关键入参；前端类须给出页面路径 + 操作元素 |
| **预期结果** | 必须**可判定**。至少包含一项：业务 `code` / HTTP 状态码 / 落库字段值 / 页面可观测表现。**禁止**写"显示正确""功能正常" |
| **数据校验** | 涉及写操作的用例建议给出核对 SQL，便于复现与留证 |

### 2.3.2 禁止事项

1. 禁止把多条独立场景塞进同一条用例（拆为 `-N` / `-B` / `-E`）。
2. 禁止在用例中写"同上"代替预期结果。
3. 禁止用例之间存在隐式依赖（若依赖，必须在前置条件中显式写出创建步骤或引用另一用例编号）。
4. 禁止只写"符合预期"而不给判定基准。

## 2.4 场景类型定义与覆盖要求

| 场景类型 | 定义 | 典型触发 | 覆盖要求 |

### 3.6.1 分页

| 项 | 事实 |
| --- | --- |
| 入参名 | `pageNo`（1 起）+ `pageSize`；**不存在 **`pageNum`。所有 `*PageQuery` DTO 均为此命名 |
| 默认值 | `pageNo = 1`、`pageSize = 10` |
| 插件上限 | `PaginationInnerInterceptor.setMaxLimit(1000L)` → `pageSize > 1000` 被截断为 1000 |

### 3.6.3 唯一索引与逻辑删除的配合（2026-10-02 按实测重写）

7 张有 `is_deleted` 的业务表唯一索引构成（`information_schema.STATISTICS` 实测）：

```
oa_user.uk_username              -> (username, active_flag)
oa_role.uk_role_code             -> (role_code, active_flag)
oa_department.uk_dept_code       -> (dept_code, active_flag)
oa_dict_type.uk_dict_type        -> (dict_type, active_flag)
oa_flow_definition.uk_flow_code  -> (flow_code, active_flag)
oa_company.uk_company_code       -> (company_code, active_flag)
oa_meeting_room.uk_room_code     -> (room_code, active_flag)
oa_menu.uk_menu_code             -> (menu_code)          -- 物理删除表，无需保护列
```

**判定规则**：对**逻辑删除**的表，删除后同编码**可立即重建**（`active_flag` 由 1 变 NULL 释放唯一键）：

- 用例预期写 `code=200`**（可重建）**；若实测 `code=5000`（`DuplicateKeyException`）→ **P1 缺陷**（逻辑删除未释放唯一编码）。
- ⚠️ 不再存在「字典/流程改写编码、用户/角色/部门未做」的两套策略差异——**该差异已于 2026-10-01 消除**，全库统一为「路径 D」。
- 多列组合唯一索引（非单列）天然规避本问题，`UniqueIndexReleaseChecker` 会跳过并只对「单列且无 `active_flag`」的索引告警。

## 5.2 判定标准

| 结论 | 定义 | 处置 |
| --- | --- | --- |
| **通过** | 实际结果与「预期结果」**完全一致**（业务码、提示文案、HTTP 状态、落库值全部吻合） | 勾选用例 |

### 5.2.1 响应约定（判定基准，2026-09-29 实测确认）

| 情形 | HTTP 状态码 | 响应体 | 说明 |
| --- | --- | --- | --- |
| 业务成功 | 200 | `Result{code=200, message, data, timestamp}` | 统一包装 |
| 业务异常 | 200 | `Result{code=业务码, message}` | **HTTP 仍为 200**，以 `code` 判定 |
| **鉴权失败**（`@PreAuthorize` 拒绝） | **200** | `Result{code=403}` | 与认证失败**不同源** |
| **认证失败**（缺令牌 / 令牌非法或过期） | **401** | `{code=401, message="未登录或登录已失效", data=null, timestamp}` | 由 `SecurityConfig.authenticationEntryPoint` **直接写出**；字段与 `Result` **同构**，但 `data` 恒为 `null` |

> **重要**：判定一律以 `code` 为准。注意 `401` 与 `403` 的 **HTTP 状态码并不同源**——`401` 是真正的 HTTP 401，`403` 是 HTTP 200 + 业务码 403。

> **已知未启用码**：`ErrorCode` 中定义的 `1005`（令牌无效或已过期）、`1006`（缺少访问令牌）**当前实现未使用**，认证失败统一返回 `code=401`。测试时**不得**按 `1005`/`1006` 判定。

### 5.2.2 关键字判定优先级

当业务码与文案同时可判定时，**以业务码为准**；文案作为辅助证据（文案调整不算缺陷，除非语义反转）。

1. 每个模块文件末尾附有该模块的**任务清单（勾选看板）**，`- [ ]` 形式，是执行进度面板。

1. 实测发现清单预期本身有误（如业务码写错）：**当场修正清单**，并在执行记录中登记为「描述修正」。
