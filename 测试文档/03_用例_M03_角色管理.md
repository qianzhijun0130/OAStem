## 模块信息

| 项 | 内容 |
| --- | --- |
| **对应接口** | `GET /system/role/page`、`GET /system/role/options`、`POST /system/role`、`PUT /system/role/{id}/status`、`DELETE /system/role/{id}`、`GET /system/role/{id}/menus`、`PUT /system/role/{id}/menus` |
| **对应页面** | `/system/role`（角色管理，含「分配权限」权限树弹窗） |
| **权限码** | `system:role:query` / `system:role:add` / `system:role:edit` / `system:role:delete` / `system:role:assign` |
| **关键业务约束** | ① `POST /system/role` 的 `/add` 与 `/edit` **共用一个端点**（`id` 为空即新增）；② `PUT /system/role/{id}/menus` 为**覆盖式全量写入**（先删后插）；③ 超级管理员（`role_code = SUPER_ADMIN`）**禁止删除、禁止改权限**；④ 分页参数名为 `pageNo` / `pageSize` |
| **依赖模块** | M02 用户管理（`oa_user_role` 关联与 `userCount` 来源）、M05 菜单管理（权限树数据源）、M01 登录与认证（重新登录后验证权限变更） |

### 本模块执行前置（在 3.2 通用前置之外）

1. `PRE-M03-1` 数据基线：`oa_role` 5 条，编码分别为 `SUPER_ADMIN`(id=1)、`DEPT_ADMIN`(id=2)、`EMPLOYEE`(id=3)、`HR`(id=4)、`FINANCE`(id=5)，`status` 均为 `1`；`oa_user_role` 仅 admin(id=1) → role_id=1 共 1 行；`oa_role_menu` 中 `role_id=1` 授权 **63** 项。
2. `PRE-M03-2` **超管角色保护是本模块最高优先级约束**：`role_id=1` 的 `role_code`、`status` 与 63 项授权**在任何用例执行前后都必须保持一致**；若用例需触碰，须先按 7.2-4 备份 `oa_role` / `oa_role_menu`。
3. `PRE-M03-3` 已按 7.1 准备 `D-ROLE-MGR`（含 `system:role:query`，**不含** `:add` / `:edit` / `:delete` / `:assign`）与 `D-ROLE-EMP`（**无任何** `system:role:*` 权限）两个临时角色；其中 `D-ROLE-EMP` 已绑定 1 个测试账号以便登录取令牌。
4. `PRE-M03-4` 已准备至少 2 个「空闲角色」（无任何用户绑定、已分配若干菜单）用于删除与授权用例；已准备至少 1 个「被占用角色」（有 1 个测试账号绑定）用于 TC-ROLE-06。
5. `PRE-M03-5` 已确认 3.4-4「权限滞后」为**已知行为**：本模块 TC-ROLE-11 与 TC-ROLE-05 的权限生效验证**必须重新登录后取新令牌**；TC-ROLE-11 则刻意使用旧令牌，结果按「已知项」记录，**不判缺陷**。
6. `PRE-M03-6` 〔源码核对提示〕`RoleServiceImpl.listOptions()` 当前未按 `status` 过滤，会返回全部角色；而 `TC-ROLE-04` 的契约要求「只返回启用状态的角色」。该差异已在用例中标注，执行时以实测为准并按 5.3-4 登记描述修正或提缺陷。
7. `PRE-M03-7` 〔源码核对提示〕`RoleServiceImpl.deleteRole` 仅执行逻辑删除，**未改写 `role_code`**，而 `uk_role_code` 唯一索引不含 `is_deleted`。故 `UC-ROLE-02-B`（删除后同编码可重建）为**重点风险回归点**。

**数据校验**

```sql
SELECT r.id, r.role_code, r.status, r.sort,
       (SELECT COUNT(*) FROM oa_user_role ur WHERE ur.role_id = r.id) AS expect_user_count

```
