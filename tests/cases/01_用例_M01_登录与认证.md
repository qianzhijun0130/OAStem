## TC-LOGIN-01 正常登录 · `P0`

> **场景覆盖**：✅ 正常　✅ 边界
> **测试维度**：功能, 回归
> **关联接口**：`POST /auth/login`

#### UC-LOGIN-01-N ｜ 超管使用正确账号密码登录成功

| 字段 | 内容 |
| --- | --- |
| **优先级** | P0 |
| **场景类型** | 正常场景 |
| **测试维度** | 功能, 回归 |
| **关联任务** | TC-LOGIN-01 |
| **关联接口** | `POST /auth/login` |

**前置条件**

1. 见 3.2 通用前置条件
2. `oa_user` 中 admin（id=1）`status=1`，密码已知

**测试步骤**

1. 发送 `POST /auth/login`，请求体 `{"username":"admin","password":"<已知密码>"}`
2. 解析响应体与 `data.token`

**预期结果**

1. HTTP 状态码 `200`
2. `code = 200`，`message = 操作成功`
3. `data.token` 为非空字符串；`data.tokenType = Bearer`
4. `data.expiresIn = 28800000`（毫秒，即 8 小时）
5. `data.username = admin`；`data.realName` 为 admin 的真实姓名
6. `data` 中**不含** `password` 字段

**数据校验**

```sql
SELECT user_id, username, login_status, ip_address, browser, os, create_time
FROM oa_login_log WHERE username='admin' ORDER BY id DESC LIMIT 1;
-- 预期：login_status=1、ip_address 非空、create_time 为当前时间附近
```

1. 依次用以下密码登录同一账号：① 含特殊字符的合法密码；② 恰好达到最小长度的合法密码

## TC-LOGIN-02 令牌结构校验 · `P0`

> **场景覆盖**：✅ 正常　✅ 异常与容错
> **测试维度**：功能, 安全
> **关联接口**：`POST /auth/login`

#### UC-LOGIN-02-N ｜ JWT 为三段式且 payload 字段完整

| 字段 | 内容 |
| --- | --- |
| **优先级** | P0 |
| **场景类型** | 正常场景 |
| **测试维度** | 功能, 安全 |
| **关联任务** | TC-LOGIN-02 |
| **关联接口** | `POST /auth/login` |

**前置条件**

1. 见 3.2 通用前置条件
2. 已用 admin 登录并取得 `data.token`

**测试步骤**

1. 将 token 按 `.` 分割，统计段数
2. Base64URL 解码第 1 段（header）、第 2 段（payload）
3. 统计 `perms` 数组长度

**预期结果**

1. 段数 = `3`
2. header 中 `alg = HS384`
3. payload 含字段：`sub`（承载用户名 `admin`）、`userId`、`roles`、`perms`、`iat`、`exp`
4. payload **不含** `username` 字段（用户名由 `sub` 承载）
5. `perms` 为字符串数组，长度 = admin 全部菜单 / 按钮权限码之和（基线为 **63**；2026-09-29 新增 `system:user:import` 后由 62 变更）
6. `exp - iat = 28800`（秒），即 8 小时

**数据校验**

```sql
-- 交叉核对：perms 条数应与超管被授权且启用的权限码数量一致
SELECT COUNT(*) FROM oa_menu m
JOIN oa_role_menu rm ON rm.menu_id = m.id
WHERE rm.role_id = 1 AND m.menu_type = 3 AND m.status = 1;
```

#### UC-LOGIN-02-E ｜ 令牌在有效期内不被服务端主动失效（已知行为确认）

| 字段 | 内容 |
| --- | --- |
| **优先级** | P2 |
| **场景类型** | 异常与容错 |
| **测试维度** | 安全, 回归 |
| **关联任务** | TC-LOGIN-02 |
| **关联接口** | `GET /auth/info` |

**前置条件**

1. 见 3.2 通用前置条件
2. 已取得一个有效 token

**测试步骤**

1. 调用 `POST /auth/logout`
2. 使用**同一个 token** 再次请求 `GET /auth/info`
3. 将某账号置为禁用，随后用其**已签发**的 token 请求 `GET /auth/info`

**预期结果**

1. `logout` 返回 `code = 200`（服务端仅作记录，不做令牌吊销）
2. 旧 token **仍能访问成功**（`code = 200`）→ 符合 3.4-5「JWT 无状态」设计
3. 禁用账号的旧 token **仍可用**至过期

5. **核心判定**：登录成功后落在工作台，**全程不出现 404**

> **回归背景（必读）**：本用例对应一个已修复的前端路由缺陷，**2026-09-29 实测复现并修复**。
> `router/index.ts` 原先**未声明** `/` 路由，同时 `router/dynamic.ts` 的兜底路由 `/:pathMatch(.*)*` 带的是**路由级 `redirect: '/404'`**——路由级 redirect 在全局守卫 `permission.ts` **之前**执行。于是：
> ① 首次导航到 `/` 时路由表里没有 `/`，守卫以 `to.path === '/'` 进入，触发 `loadUserInfo()` 注册动态路由；
> ② 守卫随后 `next({ ...to, replace: true })` 重新导航 `/`，此时兜底路由已注册，`/` 被它抢先匹配并**在守卫之前**改写成 `/404`；
> ③ 守卫第二次拿到的 `to.path` 已是 `/404`，那段「按菜单取首个可访问页」的 `/` 分支**永远不可达** → 登录后直接进 404。

>
> **修复要点**：在 `constantRoutes` 中显式声明 `/`（`name: 'Root'`，空渲染组件，真实落地页仍由守卫决定），使静态路径 `/` 的匹配权重高于兜底路由；登录页默认跳转目标由硬编码 `/dashboard` 改为 `/`；404 页「返回首页」按钮与顶栏面包屑「首页」链接同步改为 `/`。**若实测仍落在 `/404`，按 P0 回归失败登记。**

> #5 disabled=true  is-loading
> 请求时间线：61 ms、189 ms（共 2 次）

> await userStore.login(form)
> router.push(redirect)     // ← 异步且未 await
> ...
> } finally {
>   loading.value = false   // ← 立即复位，但页面还没跳走
> }

> 4. **成功后刻意不复位 `loading`**（页面随即卸载）；仅校验失败 / 登录失败 / 跳转异常时复位，保证可重试

**根因修正（描述修正）**：原记「`loading` 置位晚于 `await validate()`」，经修复前 / 修复后**对照实验证伪** —— 两轮的按钮状态序列与请求时间线完全一致，`#2`/`#3` 点击均被 `is-loading` 挡住，而 `#4` 点击时按钮已恢复可点（`disabled=false`）。真实成因是 `router.push()` 异步未 `await` + `finally` 立即复位 `loading` 形成的「请求已返回、页面未跳走」窗口。

**修复文件**：`vue3-admin-template/src/views/login/index.vue`（纯前端，1 个文件）

1. 入口闸门 `if (loading.value) return`（覆盖按钮点击 + 表单回车）
