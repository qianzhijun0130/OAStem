## 2026-10-22-01 Redis 存储接入（无 DDL，仅外部存储与 key 规划）

**本次没有任何 DDL/数据变更**，MySQL 结构不变；记录的是新增的外部存储约定。

- 实例：本机 `D:/Program Files/Redis`，Redis **3.0.504**（Windows 版），端口 6379，db 0，无密码。
- ⚠️ 该实例**已被其他项目共用**（存在 `login:token:admin` 等键），因此本项目所有键统一加前缀 `oastem:`，禁止裸键。

| key | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `oastem:auth:blacklist:{sha256前32位}` | string | 令牌剩余寿命 | 登出后令牌立即失效 |
| `oastem:dict:items:{dictType}` | string(JSON) | 600s | 字典项缓存，写操作主动删除 |
| `oastem:auth:login:fail:{username}` | counter | 300s | 失败计数窗口 |
| `oastem:auth:login:lock:{username}` | string | 300s | 临时锁定标记 |

- Redis 3.0 **不支持 `UNLINK`**（6.0+），代码中统一用 `DEL`；批量清理用 `SCAN` 游标而非 `KEYS`。
- ⚠️ Windows 版 `redis-cli --scan --pattern` 存在兼容问题（返回空），排查时请直接用 `redis-cli keys "oastem:*"`。

## 2026-10-09-02 修正表单管理菜单可见性与 FormCreate 规则类型名

**改动类型**：数据修复（**无 DDL**）

### 一、菜单可见性修正（修 404）

`/auth/menus` 的查询条件含 `.eq(Menu::getVisible, 1)`，**`visible=0` 的菜单节点不会返回**。而本项目的 `/auth/menus` 同时是「侧边栏数据源」与「前端动态路由注册源」，因此原设计「用 `visible=0` 做隐藏子页（只注册路由不进侧边栏）」不成立 —— 节点被整体排除，`/system/form/designer` 与 `/system/form/preview` 路由从未注册，点「编辑/设计」必然落 404。

```sql
UPDATE oa_menu SET visible = 1 WHERE id IN (101, 102);
```

副作用核验：侧边栏只渲染两级（目录 → 菜单），101/102 属三级节点，**即使 `visible=1` 也不会出现在侧边栏**，实测确认侧边栏仍只有「表单管理」一项。

⚠️ **项目约定**：`visible` 只能控制「是否进侧边栏」，**没有「隐藏但仍注册路由」的机制**。需要非侧边栏页面时，只能靠菜单层级（三级）来规避。

### 二、FormCreate 规则类型名修正

FormCreate 的内置类型名与 Element Plus 组件短名不同，原种子数据写错导致**日期控件完全不渲染**：

| 表/字段 | 原值 | 修正为 |
| --- | --- | --- |
| `oa_form.rule_json` | `"type":"date"` | `"type":"datePicker"` |
| `oa_form.rule_json` | `"type":"number"` | `"type":"inputNumber"` |
| `oa_form.field_schema` | `"type":"date"` / `"number"` / `"text"` | `"datePicker"` / `"inputNumber"` / `"input"` |

同时在 `oa-system/数据库/form_tables.sql` 的 `rule_json` 字段注释里补上正确/错误类型名对照表，避免后续重建数据库时复现。

**验证结果**
```
菜单：id 101/102 visible=1，/auth/menus 已返回 3 个 form 节点（100/101/102）
oa_form：leave_apply 与 expense_apply 的 rule_json 全部为 datePicker/inputNumber/select/textarea/input
field_schema：类型名与 rule_json 一致
浏览器实测：侧边栏仍只有「表单管理」；预览页 4 个字段标签全部渲染
```

## 2026-10-01-01 逻辑删除唯一索引改造（路径 D）：7 张表加生成列 active_flag + 唯一索引改复合键

**改动类型**：表结构变更（索引 + 新增生成列）+ 历史数据修复
**原因**：用户「选择行业内最推荐的方案执行」。MySQL 无 PostgreSQL 的 partial unique index（`WHERE is_deleted = 0`），业界通行替代手法是**生成列 + 复合唯一索引 + NULL 语义**。
**前置安全网**：全量备份 `F:/tmp/pathD_backup/backup_pathD_202610010100.sql`（7 张表，含 CREATE + INSERT）；DDL 前置检查确认 7 张表均无「同编码多行存活」（否则新唯一索引建不上）。

### 一、变更内容

对 7 张表统一执行：

```sql
ALTER TABLE <t>
  ADD COLUMN active_flag TINYINT
      GENERATED ALWAYS AS (IF(is_deleted = 0, 1, NULL)) VIRTUAL
      COMMENT '仅供唯一索引使用：存活=1，已删=NULL（利用 MySQL 唯一索引允许多个 NULL）',
  DROP INDEX <uk_x>,
  ADD UNIQUE KEY <uk_x> (<编码列>, active_flag);
```

| 表 | 唯一索引 | 编码列 |
| --- | --- | --- |
| `oa_user` | `uk_username` | `username` |
| `oa_role` | `uk_role_code` | `role_code` |
| `oa_department` | `uk_dept_code` | `dept_code` |
| `oa_dict_type` | `uk_dict_type` | `dict_type` |
| `oa_flow_definition` | `uk_flow_code` | `flow_code` |
| `oa_company` | `uk_company_code` | `company_code` |
| `oa_meeting_room` | `uk_room_code` | `room_code` |

**原理**：存活行 `active_flag=1` → 唯一索引按 `(编码, 1)` 约束，同编码只能有一条存活行；已删行 `active_flag=NULL` → MySQL 唯一索引允许多个 NULL，故任意多条已删行互不冲突。等价于 PostgreSQL 的 `CREATE UNIQUE INDEX ... WHERE is_deleted = 0`。

**未改动**：`is_deleted` 保持 `TINYINT NOT NULL DEFAULT 0`（0/1 语义），符合《阿里巴巴 Java 开发手册》建表规约对 `is_xxx` 字段的要求。
