### 三、测试脚本两个工程坑（沉淀）

1. **`SET FOREIGN_KEY_CHECKS=0` 跨 mysql 进程失效**：每个 `mysql.exe -e` 是独立会话，FK 检查重置为 1 → 按外键顺序删不动。修法：全部 DELETE 与 SET 合并进**单次 `-e` 多语句**。

## 2026-09-28-03 技术选型论证（实测结论）

### ORM：不建议 MyBatis-Plus + JPA 混用

用户提议「复杂联表用 MyBatis-Plus，简单查询用 JPA」。技术上可行（两者共用 `DataSourceTransactionManager`，同一事务可共存），但工程代价明确：

| 风险 | 说明 |
|---|---|
| 一级缓存脏读 | JPA 的持久化上下文会缓存实体，MyBatis-Plus 直接 UPDATE 数据库后，JPA 侧同事务内仍读旧值 |
| 实体类职责冲突 | 同一个类要同时满足 `@Entity`（JPA）与 `@TableName`（MP）两套约定 |
| 机制双份 | 逻辑删除（`@SQLRestriction` vs `@TableLogic`）、审计字段填充（Auditing vs MetaObjectHandler）、分页类型（`Page` vs `IPage`）各两套 |
| 认知与风格割裂 | 同一个查询需求有两种写法，长期维护成本高 |

**结论**：用户想要的「简单查询省事」，MyBatis-Plus 的 `BaseMapper` + `LambdaQueryWrapper` 已能提供接近 JPA 的零 SQL 体验，复杂联表用 XML `@Select` 写原生 SQL 即可。单一 ORM 优于双 ORM。

### 认证：Spring Security + JWT

已确认采用。计划文档即为此方案，行业标准，资料充分。

### 审批引擎：Flowable vs 自建四表

**版本查证（关键）**：Flowable 7.x 与 Spring Boot 4.1.1 存在版本错配风险——7.2.0 的 autoconfigure 依赖 `spring-boot-starter-web`，而该 starter 在 Boot 4 中官方描述为「deprecated in favor of spring-boot-starter-webmvc」；Flowable **8.0.0** 已改用 `spring-boot-jdbc` / `spring-boot-jackson` 等 Boot 4 模块名。若采用 Flowable，应选 **8.0.0** 而非 7.x。

**表数量**：`flowable-engine` 8.0.0 的 MySQL 建表脚本实测为 engine 7 张 + history 5 张 = **12 张**；其余模块（任务、变量、作业、身份链接、IDM 等）的表分散在其他 jar，未能逐一实测，实际启用后估算在 **25–35 张**区间。此前「约 20 张」的说法偏低，予以修正。
