## 2026-10-05-02 日志分级查询与清理（超管 / 部门负责人 / 普通用户三档）

**改动类型**：功能增强（数据权限分级 + 清理加固）
**触发**：用户需求「实现日志管理模块，基于现有角色权限体系与用户-部门归属关系，实现日志的分级查询与清理」。
**范围**：后端 6 个文件（1 新建）、前端 4 个文件；**无 DDL**。

### 一、前置判断：并非从零开发
日志模块已存在 `page` / `export` / `clean`（含 `archiveBefore` 归档 + `@OperationLog` 审计）。
真正缺失的是：**分级数据权限**、`userId` 筛选、全量清理、清理护栏。

### 二、新增 `LogScopeResolver`（核心）

**为什么不能直接复用 `@DataScope` + `applyTo`**：日志表的行归属人是「操作人 `user_id`」，
而 `oa_user` 的行归属是「部门 `dept_id`」；日志表**既无 `dept_id` 也无「操作人部门」列**，
`applyTo(wrapper, deptColumn, idColumn)` 的前提不成立。故先把范围解析成**可见 user_id 集合**，
再以 `user_id IN (...)` 落进查询。

| 档位 | 判定依据 | 范围 |
| --- | --- | --- |
| 超级管理员 | `data_scope = ALL`（`DataScopeSupport#prepare` 中只有 `SUPER_ADMIN` 得到 ALL） | **不限** |
| 部门负责人 | 持日志查询权限码 **且** `data_scope = DEPT` | **本部门 + 全部下级部门**成员 |
| 普通用户 | 其余 | **仅本人** |

> **关键安全设计**：「能配多大数据范围」与「能看审计日志」是**两件事**。
> 无查询权限码者**一律收敛为仅本人**，绝不因其 `data_scope=2` 而被放大。
> 实测佐证：`hr_staff1` 的 `data_scope=2`，但因无日志查询权限，可见范围仍为「仅本人」。

### 四、三个安全决策

1. **`page` 端点鉴权放宽为「登录即可」**：「查看自己的日志」是**个人权限**而非管理权限，
   若沿用 `system:*-log:query` 会让普通员工 403 而看不到自己的操作记录。
   范围改由 Service 层**强制注入**，前端只做隐藏不构成安全边界。
   `export`（批量外流）仍保留管理权限，未放宽。

2. **越权返回空集而非 403**：`userId` 只能在范围内收窄；越权或不存在一律 `200 + total=0`。
   这样既不泄露「该用户是否存在」，也不会让正常操作突然失败。

3. **全量清理的审计保护**：分界取「**本次请求开始时刻**」而非 `now + 1`。
   `@OperationLog` 写入的审计日志 `create_time` 必然晚于该分界 → `create_time < cutoff` 不成立
   → **这条审计日志既不会被归档、也不会被这次清理自己删掉**。
   另加**保留期护栏**：按时间清理时必须保留 ≥1 天（`MIN_KEEP_DAYS`），
   否则「把截止时间设成 5 分钟前」等于变相擦除痕迹。

**为什么需要定制而不能直接 `applyTo`**

**数据范围口径（最终）**
- `ALL` → 全放行；`DEPT` → 本部门及其所有下级部门；`SELF` → 收敛为仅本部门
- 用户无归属部门 → **返回空集合**（数据权限属安全边界，宁可少给不误放开）

## 2026-10-01-02 逻辑删除唯一索引改造落地（路径 D：生成列 + NULL 语义，含 7 张表 DDL）



**改动类型**：数据库结构变更（DDL）+ 代码重构（移除应用层占位改写）+ 自检器判据升级

**原因**：用户「选择行业内最推荐的方案执行」。MySQL 无 PostgreSQL 的 partial unique index，业界通行替代手法是**生成列 + 复合唯一索引 + NULL 语义**（方案文档 v2 §1/§5）。



### 一、数据库变更（7 张表）



```sql

ALTER TABLE <t>

  ADD COLUMN active_flag TINYINT

      GENERATED ALWAYS AS (IF(is_deleted = 0, 1, NULL)) VIRTUAL

      COMMENT '仅供唯一索引使用：存活=1，已删=NULL（利用 MySQL 唯一索引允许多个 NULL）',

  DROP INDEX <uk_x>,

  ADD UNIQUE KEY <uk_x> (<编码列>, active_flag);

```



| 表 | 唯一索引 | 编码列 |

| --- | --- | --- |

| `oa_user` | `uk_username` | `username` |

| `oa_role` | `uk_role_code` | `role_code` |

| `oa_department` | `uk_dept_code` | `dept_code` |

| `oa_dict_type` | `uk_dict_type` | `dict_type` |

| `oa_flow_definition` | `uk_flow_code` | `flow_code` |

| `oa_company` | `uk_company_code` | `company_code` |

| `oa_meeting_room` | `uk_room_code` | `room_code` |



原理：存活行 `active_flag = 1` → 唯一索引按 `(编码, 1)` 约束，同编码只能有一条存活行；已删行 `active_flag = NULL` → MySQL 唯一索引允许多个 NULL，故任意多条已删行互不冲突。

#### 缺陷 1（严重）：新增用户必然 5000——`company_id` 从未赋值



- **现象**：`POST /system/user` 报 `{"code":5000,"message":"系统内部错误"}`。

- **现象**：`DELETE /system/login-log/clean`（不传 `before`）返回 `5000 系统内部错误`。服务层里明明有 `before == null` 校验，却成了死代码。

- **成因**：控制器用 `@RequestParam`（默认 `required = true`），参数缺失时 Spring 在**方法体执行前**就抛 `MissingServletRequestParameterException`；全局处理器没有对应分支，落进兜底 `Exception` → 5000。同类问题还有参数类型转换失败（如 `before=abc`）。另外 `ErrorCode` 里 `METHOD_NOT_ALLOWED(405)`、`NOT_FOUND(404)` 早已定义却从未被使用。

- **处置**：`GlobalExceptionHandler` 补 4 个分支——`MissingServletRequestParameterException`（`缺少必填参数: xxx`）、`MethodArgumentTypeMismatchException`（`参数格式不正确: xxx`）、`HttpRequestMethodNotSupportedException`（405）、`NoResourceFoundException`（404，不打堆栈）。

#### 缺陷 3（中）：`#{#before}` 未解析，日志里留下原始模板



- **现象**：`operation` 字段存的是字面量 `清理登录日志 #{#before}`，而同机制的 `发布公告 #{#id}` 却能正常解析成 `发布公告 1`。

- **定位**：写了一个隔离探针（`-parameters` 编译，直接调用 `MethodBasedEvaluationContext` + `TemplateParserContext`）复现，拿到确切原因：



  ```

  EL1001E: Type conversion problem, cannot convert from java.time.LocalDateTime to java.lang.String

  cause: ConverterNotFoundException: No converter found capable of converting from type

         [java.time.LocalDateTime] to type [java.lang.String]

  ```



  根因是 `resolveOperation` 里调用了 `.getValue(context, String.class)`，依赖 SpEL 默认的 `StandardTypeConverter`（底层 `DefaultConversionService`）。它只认显式注册的类型转换器：`Long -> String` 能转，`LocalDateTime -> String` 转不了；异常被 catch 静默吞掉后回退成原始模板。**Bean 字节码中 `MethodParameters` 属性正常存在，参数名发现机制没有问题**，排除了「参数名缺失」这一常见猜测。

- **处置**：保留 `TemplateParserContext`，给求值上下文装一个宽松的 `TypeConverter`（`DefaultConversionService` + 显式 `Object -> String` 转换器，统一走 `String.valueOf`）；同时把 catch 里的静默吞异常改为 `log.debug`，便于日后定位注解写错这一类问题。

### 二、本轮发现并修复的 2 个缺陷



#### 缺陷 1（严重）：菜单 id=60 冲突，覆盖了「发起审批」按钮

- **现象**：`oa_menu` 中 id=60 的 `menu_name` 是「系统字典」，`menu_code` 却是 `system:approval:start`。

- **成因**：`数据库/stage4_menu.sql` 用固定 `id=60` 插入字典菜单，而 `flow_menu.sql` 里 id=60 早已是「发起审批」按钮。`INSERT ... ON DUPLICATE KEY UPDATE` 命中主键后执行 UPDATE，但 UPDATE 子句不含 `menu_code`，该列便保留了原值。

- **影响**：① 原「发起审批」按钮行被改写成页面菜单（parent 由 52 变 10），审批模块缺了按钮权限；② 字典菜单编码错误，语义混乱。

- **处置**：新增一次性脚本 `数据库/fix_menu_id60_conflict.sql`（执行前已 `mysqldump` 备份 `oa_menu` + `oa_role_menu`）——恢复 id=60 为「发起审批」按钮，字典菜单迁到空闲 id=70，字典按钮权限 66~69 改挂 70；`stage4_menu.sql` 改为写 id=70，并在注释里写明「不要随手定 id，先确认未被占用」。



#### 缺陷 2（轻）：字典表时间字段默认值为 NULL

- **现象**：脚本插入的 4 条字典类型 `create_time`/`update_time` 均为 NULL，接口新增的记录却有值。

- **成因**：`dict_tables.sql` 的 DDL 写的是 `create_time DATETIME DEFAULT NULL`，与项目其它表（`NOT NULL DEFAULT CURRENT_TIMESTAMP`）不一致；且 `INSERT ... SELECT ... WHERE NOT EXISTS` 未显式传这两列。

- **处置**：改脚本 DDL 为 `NOT NULL DEFAULT CURRENT_TIMESTAMP`（`update_time` 加 `ON UPDATE`）；线上先 `IFNULL` 回填再 `ALTER TABLE`。

## 2026-09-29-06 修复：流程标识归一化 + 一致性自检（方案 A+B）



**改动类型**：缺陷修复（高危——发起流程会执行到别的模板）



### 成因回顾



引擎的流程定义 key 取自 BPMN 的 `<process id>`，发起流程走 `startProcessInstanceByKey`（按 key 取**最新版本**）。设计器新建画布的默认值是 `process_1`，多个模板共用同一 id 时后部署者顶掉先部署者。



### 方案 A：部署前统一归一化



- **新增 `workflow/util/BpmnXmlNormalizer.java`**：把 `<process id>` 改写为流程编码，并同步改写 `<bpmndi:BPMNPlane bpmnElement>` 对它的引用（不改会令 bpmn-js 重新打开时画布空白）。幂等——process id 已等于目标值或找不到 `<process>` 时原样返回；序列化用 `Transformer`，开启 `FEATURE_SECURE_PROCESSING` 并置空外部 DTD/样式表访问。

- **`workflow/util/BpmnXmlParser.java`**：`NS_BPMN` 与 `parseDocument` 由 `private` 放宽为包级可见，让归一化器复用同一套 XXE 加固配置（各自 new 一个 `DocumentBuilderFactory` 极易漏配加固项）。

- **`FlowDefinitionServiceImpl.deployAndBind`**：部署前先 `overrideProcessId(xml, fd.getFlowCode())`，用归一化后的 XML 部署与解析 key。



### 方案 B：兜底校验 + 启动自检



- **`FlowDefinitionServiceImpl.assertBpmnKeyAvailable`**：保存前查该 `bpmn_key` 是否已被**其他** `flow_code` 占用，占用即抛 `FLOW_KEY_CONFLICT`。`flowCode` 唯一性校验在其之前，此处专门拦存量脏数据与未来新增部署入口。

- **新增 `workflow/bootstrap/FlowKeyConsistencyChecker.java`**：启动扫描 `oa_flow_definition`，把「bpmn_key 重复」与「bpmn_key ≠ flow_code」的模板打到 WARN 日志并给处置建议。**只读不改**——批量改写标识会牵动 Flowable 部署，须人工确认。归一化只对**新保存**的模板生效，历史数据靠它暴露。

- **`FlowBootstrapRunner`** 加 `@Order(100)`，与 Checker 的 `@Order(200)` 拉开顺序，保证本次播种的模板也纳入体检。

- **`common/ErrorCode.java`**：新增 `FLOW_KEY_CONFLICT(3006, "流程标识已被其他流程模板占用")`。



### 前端



- `views/workflow/definition/index.vue`：流程编码项补填写指引（仅字母数字下划线、部署后不可改、流程标识会自动对齐）；导入 BPMN 时若文件用的是默认标识（`process_1` 之类）不再预填流程编码，改为提示手动填写。

## 2026-09-29-05 排查：审批中心「无权限执行该操作」与流程标识冲突



**改动类型**：排查（未改代码）+ 测试数据清理



### 问题一：审批中心子菜单提示「无权限执行该操作」



**排查结论：不是权限数据缺失，是 JWT 里的权限快照过期。**



| 检查项 | 结果 |

|---|---|

| `oa_menu` 50–55（目录 + 5 页面）、56–65（10 个按钮权限） | 全部存在，`status=1 visible=1` ✅ |

| `oa_role_menu` 对 role_id=1..5 的授权 | 50–65 全部已授权 ✅ |

| 后端权限聚合 `UserServiceImpl.getMenuCodesByUserId` | 取 role_menu → menu_code（含 menu_type=3），无过滤缺陷 ✅ |



真正的成因是两个接口的数据来源不同：



- `/auth/menus` **实时查库**（`menuService.getMenuTreeByUserId`）→ 新菜单立刻可见，所以侧边栏能出现审批中心。

- 业务接口鉴权走 `@PreAuthorize("hasAuthority(...)")`，而权限来自 **JWT 的 `perms` claim**——登录时写入、有效期 8 小时、期间不刷新（`JwtUtil` 设计为无状态）。



`数据库/flow_menu.sql` 是在用户当前令牌签发**之后**才执行的，旧令牌的 `perms` 里没有 `system:flow:*` / `system:approval:*`，于是出现「菜单看得见、点进去 403」。



**实测对照**（同一接口 `/workflow/flow-definition/page`，仅换令牌）：



| 令牌 | 结果 |

|---|---|

| 含 workflow 权限的新令牌 | HTTP 200，返回模板分页数据 ✅ |

| 缺 workflow 权限的旧令牌 | HTTP 200 + `{"code":403,"message":"无权限执行该操作"}` ❌ |

| 旧令牌调 `/auth/menus` | HTTP 200，且返回树中含审批中心子菜单 ✅（与现象完全吻合） |



**解决方式**：退出登录重新登录一次即可，**无需改代码**。长期改进项见文末。



### 问题二（新发现，高危）：新建流程的 process id 撞车



`components/bpmn/BpmnModeler.vue` 的空白模板把 `<process id>` 硬编码为 `process_1`，而 `startProcessInstanceByKey(procKey(fd))` 是按 key 启动、取**最新版本**。



**实测复现**：创建两个模板 `probe_alpha` / `probe_beta`（均沿用默认 process id）：



| 检查点 | 实测结果 |

|---|---|

| `oa_flow_definition.bpmn_key` | 两条都是 `process_1` ❌ |

| `act_re_procdef` | `process_1` 累积到 `VERSION_=2` ❌ |

| 发起 `probe_alpha` 后落库业务记录 | `flow_code=probe_alpha`（业务侧认为发的是 A） |

| 发起 `probe_alpha` 后 Flowable 实际执行 | `PROC_DEF_ID_=process_1:2` = **probe_beta 那一版** ❌ |



即：**选 A 跑 B**——流程走错审批链、表单字段错位。



**处置**：已按「方案 A 归一化 + 方案 B 兜底校验」修复，明细见 `2026-09-29-06`。



**清理**：两个临时模板、流程实例、`act_*` 历史与部署记录已全部清除，库恢复原状（`oa_flow_definition` 仅剩内置 leave/expense；`act_re_procdef`=2、`act_re_deployment`=2；`act_ru_execution` / `act_hi_*` = 0）。



**环境说明**：本次排查时后端未运行，用 `./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8080` 启动；curl 访问 127.0.0.1 必须加 `--noproxy '*'`（终端有 HTTP 代理）。

### 本轮踩到的 3 个坑（均已修复）



1. **Java 参数文件中 `--server.port` 必须放在主类名之后**。写在前会被当作 JVM 选项，直接报 `Unrecognized option` 并退出（表现为进程存在但端口不监听、日志为空）。

2. **Bash 命令里的 Windows 反斜杠会被转义破坏**（`C:\Users` → `C:\Uses\qiaz`）。生成 classpath 时统一改用正斜杠，Java 在 Windows 上完全支持。

3. **`.cmd` 脚本必须纯 ASCII**。cmd.exe 按 GBK 解析，UTF-8 中文注释会被当成命令执行导致脚本崩溃（日志表现为成片的乱码"不是内部或外部命令"）。脚本内注释已全部改为英文。



### 环境注意事项



- 本会话终端注入了 `SERVER__PORT` 环境变量，Spring Boot 松散绑定会覆盖配置文件的 `server.port`，启动时应显式带 `--server.port=8080`。

- 终端存在 HTTP 代理，curl 访问 127.0.0.1 必须加 `--noproxy "*"`，否则返回 502。

- 停止服务：`taskkill //F //PID <java_pid>`（勿用 `//IM java.exe` 全局清理，会误杀正在运行的服务实例）。

## 2026-09-28-03 回退：Java 版本 25 → 17



- **类型**：回退（撤销外部工具的改动）

- **文件**：`oa-system/pom.xml` 第 30 行 `<java.version>25</java.version>` → `<java.version>17</java.version>`



**背景**：`oa-system` 被 appmod modernize 工具（会话 `20260928082042`，08:20–16:30）自动执行了 Java 17→25 升级，并在 `C:\Java\jdk25\jdk-25.0.2` 安装了 JDK 25。



**为什么回退**：



1. 改动非我方需求，属工具自行推断

2. Spring Boot 4.1.1 本就兼容 Java 17，升级零收益（plan 文件自述无需框架升级）

3. **引入了实际故障**：`JAVA_HOME` 仍为 `C:\Java\jdk17`，Maven 用 JDK 17 编 release 25 目标 → 编译失败

4. Java 17/21 才是主流 LTS；25 会让每次运行都需手动切 JDK



**回退前的故障实证**：



```

./mvnw.cmd -B clean compile   →  退出码 1

[ERROR] Fatal error compiling: 错误: 不支持发行版本 25

```



**回退后验证**：



```

[INFO] Compiling 1 source file with javac [debug parameters release 17]

[INFO] BUILD SUCCESS   →  退出码 0 ✅

```



**遗留事项**：



- JDK 25 仍安装在 `C:\Java\jdk25\jdk-25.0.2`，保留不影响项目，可随时删除

- `oa-system/.github/modernize/` 是工具会话残留（含 UUID 与本机绝对路径），将来上 Git 时需纳入 `.gitignore`
