## 2026-10-22-05 系统内置头像：头像地址白名单放行 `/avatars/**

**改动类型**：功能增强（2 文件）

**背景**：个人中心要支持「选系统内置头像」与「上传自己的头像」两种方式。原来 `updateAvatar` 只认 `file.access-prefix`（`/uploads/`）开头的地址，内置头像（随前端发布的 `/avatars/avatar-NN.svg`）会被判非法。

### 一、改动

| 文件 | 改动 |
| --- | --- |
| `profile/support/BuiltinAvatars.java`（新增） | 内置头像**精确白名单**：`COUNT=12`，路径 `PATH_PREFIX + "avatar-%02d.svg"`，`contains()` 只做 `Set.contains`，`all()` 供测试/前端对齐 |
| `profile/service/impl/ProfileServiceImpl.java` | `assertInternalUploadPath` → `assertAvatarPath`：内置白名单命中直接放行；否则仍要求 `/uploads/` 前缀，并**新增拒绝 `..`**（防路径拼接）；空值单独提示「头像地址不能为空」 |

### 二、为什么不能简单放行 `/avatars/` 前缀

前缀放行会让 `/avatars/../../etc/passwd` 这类拼接同样通过。改成「精确枚举 12 个文件名」后，越界文件名（`avatar-13.svg` / `avatar-00.svg`）与路径拼接一律拒绝，白名单即文档。

⚠️ **前后端必须同步**：前端 `src/utils/avatars.ts` 的 `BUILTIN_AVATAR_COUNT` 与 `BuiltinAvatars.COUNT` 不一致时，会出现「界面能选、保存被拒」或「存了却选不到」。

### 三、验证（`F:/tmp/verify_avatar.py` 13/13）

- 12 个内置头像逐个 `PUT /profile/avatar` → 均 200 且 `GET /profile/info` 能读回；
- 拒绝项 8 条：`avatar-13` / `avatar-00` / `/avatars/../etc/passwd` / 外部 URL / `/static/a.png` / `/uploads/../../a.png` / `""` / 纯空白，全部 400；

## 2026-10-22-03 新建员工默认绑定「普通员工」角色

**改动类型**：行为调整（后端 2 文件）

**需求**：新建员工时系统自动添加角色范围「普通员工」，后续角色由管理员添加。

### 一、问题

`UserSaveRequest.roleIds` 是 `@NotNull @Size(min=1)`，且 `createUser` 只按传入值绑定。直接调接口（脚本/导入/第三方）不传角色时，会造出**能登录但侧边栏空白、所有接口 403** 的账号——不是「权限收敛」，而是「账号不可用」。

### 二、改动

| 文件 | 改动 |
| --- | --- |
| `UserSaveRequest` | `roleIds` 去掉 `@NotNull / @Size(min=1)`，改为 `@Size(max=20)`：允许留空，语义交给服务层 |
| `UserServiceImpl#createUser` | 空角色 → `requireDefaultRoleId()` 解析 `role_code='EMPLOYEE'` 并绑定；角色缺失时抛 `ROLE_NOT_FOUND` 并给出可操作提示（而非静默建出无角色账号） |
| `UserServiceImpl#updateUser` | 留空视为「本次不改动角色」，保留原绑定（不先删后插）。避免局部保存把账号清成无角色状态 |

**为什么默认角色按 `role_code` 取而不是写死 id**：id 会随环境变化，`role_code` 是稳定标识；角色名可被管理员改（如「基层员工」），也不能按名称匹配。

**为什么更新时空值不清空**：前端已强制至少一个角色，接口层收到空大概率是「没带这个字段」而非「要清空」；清空的结果是账号不可用，不做静默破坏。

### 三、验证

`F:/tmp/verify_default_role.py` **8/8**：

| 场景 | 结果 |
| --- | --- |
| 不传 `roleIds` | 落库 `['EMPLOYEE']`，可用初始密码登录，菜单树 14 节点（非空） |
| 传 `roleIds: []` | 同样回落 `EMPLOYEE` |
| 显式传 `[HR]` | 只有 `HR`，**不叠加**默认角色 |
| 编辑不带 `roleIds` | 原 `EMPLOYEE` 保留，未被清空 |
| 清理 | 测试账号与关联行物理删除，残留 0 |

浏览器 `F:/tmp/default_role_ui.js` **6/6**：新增弹窗默认选中「普通员工」（仅 1 个）、说明文案可见、下拉仍可追加其它角色、清空角色后保存被「请至少分配一个角色」拦住。

**回归**：`pages_smoke.js` 11/11、`x2_matrix.py` 18/18（权限矩阵未受影响）。

### 四、对既有测试用例的影响

`02_用例_M02_用户管理` 中「新建用户必须传 roleIds」的断言前提已变化：现在留空会成功并绑定 EMPLOYEE。若重跑该模块，需把这类断言从「400 必填」改为「默认 EMPLOYEE」。

## 2026-10-22-02 修复 D1（flow_config 清空断裂）+ 部署前校验顺序 + 登记 D10

**改动类型**：缺陷修复（后端 2 文件）+ 缺陷登记

### 一、D1 修复：可清空列真正能清空

**文件**：`workflow/service/impl/FlowDefinitionServiceImpl.java`

**现象**：保存接口传 `flowConfig: null` / `""`，库里旧值仍在（DTO 注释承诺「传 null 清空全部可视化条件」落不了地）。同族：`icon`、`category`、`remark`、`nodeConfig` 清不掉。

**根因**：`updateById(部分实体)` 走 MyBatis-Plus 的 **NOT_NULL 更新策略**，null 字段被从 `SET` 里剔除。

**修复**：
1. 改用 `LambdaUpdateWrapper` **显式 set 每一列**（含 null），不再依赖实体非空判断；
2. 新增 `blankToNull()`，把空串/空白统一归一为 `NULL`（避免库里「未配置」同时存在 `''` 与 `NULL` 两种表示）；
3. **显式 set `update_time`**：wrapper 更新不触发 `MetaObjectHandler` 自动填充，而本表 DDL 也没有 `ON UPDATE CURRENT_TIMESTAMP`（实测 `update_time` 只由填充写入），漏掉这一行会让时间停在旧值。

### 二、引擎侧：清空条件必须同时删掉注入过的表达式

**文件**：`workflow/util/BpmnXmlNormalizer.java`（新增重载）、`FlowDefinitionServiceImpl`（传入历史连线 id）

**问题**：设计器画布是从**已部署 BPMN** 加载的，里面带着上次注入的 `<conditionExpression>`。只改 `flow_config` 不清理 XML，运行期仍按旧条件路由——即「界面清空了、流程行为没变」，与 D1 是同一个用户可见症状的两个环节。

**修复**：`injectConditions(xml, items, previouslyInjectedFlowIds)` —— 只删除「**上次由本系统注入、本次已不在配置里**」的连线表达式；内置模板手写的 `${outcome == 'approve'}` 从未出现在 `flow_config` 中，不受影响。清理时**保留网关 `default` 属性**（默认分支可以没有条件，保留才能过结构校验）。

**边界（已在 DTO 注释写明）**：清空条件且画布仍是从排他网关分出多条线时，部署会被结构校验拒绝（**3005**，非默认分支既无条件也非默认）。这是正确的——这种图形本身跑不通，需要先在画布上改掉网关，而不是让后端猜一个路由。

### 三、顺带修掉：保存失败会先删掉线上部署

**问题**：`updateExisting()` 原先在 `deployAndBind()` **之前**调用 `engineService.undeploy()`，而 `deleteDeployment(id, true)` 是**级联删除**。一次校验不通过的保存，会把线上部署连同在跑实例一起删掉，表现为「保存报错 → 流程从发起页消失」。

**修复**：把卸载移到 `deployAndBind()` 内部、**所有校验之后**、真正 `deploy()` 之前。

### 四、缺陷登记（**未修复**，待授权）

| --- | --- | --- | --- | --- |

## 2026-10-22-01 接入 Redis（登出黑名单 + 字典缓存 + 登录失败限流）

**改动类型**：新依赖 + 基础设施能力（4 个新类 + 3 处业务接入）

### 一、依赖与配置
- `pom.xml` 新增 `spring-boot-starter-data-redis`（本地仓库已有 4.1.1 / Lettuce 7.5.2，离线可编译）；
- `application.properties` 新增 `spring.data.redis.*`、`redis.fail-fast`、`redis.cache.dict-ttl-seconds`、`security.login.*`。

⚠️ **不写 `spring.data.redis.password`**：本地 Redis 3.0 未设 requirepass，而 Lettuce 对空串密码仍会发送 AUTH，
会直接报 `ERR Client sent AUTH, but no password is set` 导致连不上。需要密码时用环境变量 `REDIS_PASSWORD` 注入。

### 二、新增类（`common/redis` + `security`）
| 类 | 职责 |
| --- | --- |
| `RedisGuard` | 统一访问入口：所有 Redis 操作包异常并降级；失败后 30s 熔断冷却（避免每个请求各等 3s 超时），冷却结束半开重试 |
| `RedisStartupChecker` | 启动 ping + 记录版本；失败按 `redis.fail-fast` 决定告警或中止 |
| `TokenBlacklistService` | 登出黑名单，key = SHA-256 令牌摘要前 32 hex（不存明文令牌） |
| `LoginFailureGuard` | 登录失败计数与临时锁定（按账号维度，不按 IP） |

### 三、业务接入
1. **登出即时失效**（`AuthController#logout` + `JwtAuthenticationFilter`）：登出时按令牌剩余寿命写黑名单；过滤器解析令牌后先查黑名单，命中则不建立认证上下文 → 返回 401。这是本次最有价值的改动——原实现登出只清前端存储，令牌在 8 小时内仍可被重放。
2. **字典缓存**（`DictDataServiceImpl#listByType`）：读时 `RedisGuard.read` 命中即返回，未命中回源并回写（TTL 600s）；`saveData` / `deleteData` / `updateStatus` 及 `DictTypeServiceImpl` 的增删改状态**主动失效**（类型新建也要失效：类型不存在时「空列表」会被缓存）。
3. **登录限流**（`AuthServiceImpl#login`）：认证前查锁定，失败计数达 5 次锁定 5 分钟，成功清零；`Disabled/Locked` 不计入（不是猜密码）。新增错误码 `LOGIN_TOO_MANY_FAILURES(1008)`，与「账号被管理员锁定 1003」区分。

### 四、关键取舍
- **Redis 故障一律降级、不阻断业务**：缓存回源、黑名单放行、限流关闭。理由是三者都是增强能力，若因缓存故障让全站 500 或全员登录失败，损失远大于「已登出令牌短暂可用」。
- **key 全部加 `oastem:` 命名空间**：本机 Redis（db 0）已被其他项目使用（存在 `login:token:*` 键），不加前缀会撞键。
- **只用 `StringRedisTemplate` + 显式 JSON**：不启 Jackson default typing，避免反序列化任意类的安全风险；Redis 里存的是可读 JSON，排查方便。

`mvn -o -q compile` 通过；启动日志 `[Redis 检查] 连接正常：PONG | redis 3.0.504`，菜单 82 / 声明码 54 校验器零缺口。

## 2026-10-12-01 阶段一：表单复用链 + 审批区（需求 3/4/5）

### 一、表单字段平铺为流程变量（`ApprovalServiceImpl#start`）

原实现只把整包表单塞进 `vars.formData`（一个 JSON 字符串），**BPMN 条件表达式无从引用具体字段** —— `node_config` 里没有条件能力，后端也无任何 `conditionExpression` 处理。

新增 `flattenFormData()`，把表单每个顶层字段提升为独立流程变量，使 `${days > 3}` 可直接求值：

| 关键处理 | 理由 |
| --- | --- |
| 字符串尽量还原为 `Integer`/`Double` | Flowable 表达式对数值运算敏感，`"5"` 与 `5` 比较结果不同 |
| 优先 `Integer` 再 `Double` | 避免 `3` 变成 `3.0` 影响展示与比较 |
| 跳过非法标识符键（数字开头/含空格） | 表达式解析会失败 |
| 跳过 `RESERVED_VARS`（formData/applicantId/title） | 防止表单里的同名字段覆盖内建变量导致标题错乱 |
| 非法 JSON 返回空表 + `log.warn` | 表本是可选的，不应因格式问题让流程发不起来 |
| 嵌套对象/数组不提升 | 保留在 formData 里由应用层解析，避免复杂对象污染变量命名空间 |

7. **Jackson 3**：本项目 Spring Boot 4 用 `tools.jackson`，非 `com.fasterxml.jackson`；`ObjectMapper` 由构造器注入，不用 `new`。

1. **包路径与包声明不一致**：`NodeFormBindRequest.java` 建在 `workflow/dto/` 下却写成 `package ...system.dto;` → 报「类重复」，且**连锁导致 Lombok 注解处理器中断**，全项目 `log`/`getCode()` 一起报错。改回正确包名即恢复。
2. **`PageResult` 无无参构造器**：应用 `PageResult.of(records, total, pageNo, pageSize)` 工厂方法。

## 2026-10-05-02 日志分级查询与清理（超管 / 部门负责人 / 普通用户三档）

**改动类型**：功能增强（数据权限分级 + 清理加固）
**触发**：用户需求「实现日志管理模块，基于现有角色权限体系与用户-部门归属关系，实现日志的分级查询与清理」。
**范围**：后端 6 个文件（1 新建）、前端 4 个文件；**无 DDL**。

### 一、前置判断：并非从零开发
日志模块已存在 `page` / `export` / `clean`（含 `archiveBefore` 归档 + `@OperationLog` 审计）。
真正缺失的是：**分级数据权限**、`userId` 筛选、全量清理、清理护栏。

### 二、新增 `LogScopeResolver`（核心）

**为什么不能直接复用 `@DataScope` + `applyTo`**：日志表的行归属人是「操作人 `user_id`」，
而 `oa_user` 的行归属是「部门 `dept_id`」；日志表**既无 `dept_id` 也无「操作人部门」列**，
`applyTo(wrapper, deptColumn, idColumn)` 的前提不成立。故先把范围解析成**可见 user_id 集合**，
再以 `user_id IN (...)` 落进查询。

| 档位 | 判定依据 | 范围 |
| --- | --- | --- |
| 超级管理员 | `data_scope = ALL`（`DataScopeSupport#prepare` 中只有 `SUPER_ADMIN` 得到 ALL） | **不限** |
| 部门负责人 | 持日志查询权限码 **且** `data_scope = DEPT` | **本部门 + 全部下级部门**成员 |
| 普通用户 | 其余 | **仅本人** |

> **关键安全设计**：「能配多大数据范围」与「能看审计日志」是**两件事**。
> 无查询权限码者**一律收敛为仅本人**，绝不因其 `data_scope=2` 而被放大。
> 实测佐证：`hr_staff1` 的 `data_scope=2`，但因无日志查询权限，可见范围仍为「仅本人」。

### 三、修改文件

| 文件 | 改动 |
| --- | --- |
| `system/service/support/LogScopeResolver.java` | **新建**：三档范围解析 + 部门子树展开（内存逐轮收敛，不递归查库） |
| `system/dto/OperationLogPageQuery.java` / `LoginLogPageQuery.java` | 新增 `userId` 精确筛选 |
| `system/service/impl/OperationLogServiceImpl.java` / `LoginLogServiceImpl.java` | `page`/`export` 加 `@DataScope`；`buildWrapper` 注入范围条件；`clean(before, all)` + `resolveCleanCutoff` 护栏 |
| `system/service/OperationLogService.java` / `LoginLogService.java` | `clean` 签名加 `all` |
| `system/controller/OperationLogController.java` / `LoginLogController.java` | `page` 去掉 `@PreAuthorize`；`clean` 改 `hasRole('SUPER_ADMIN')` + `all` 参数 |

### 四、三个安全决策

1. **`page` 端点鉴权放宽为「登录即可」**：「查看自己的日志」是**个人权限**而非管理权限，
   若沿用 `system:*-log:query` 会让普通员工 403 而看不到自己的操作记录。
   范围改由 Service 层**强制注入**，前端只做隐藏不构成安全边界。
   `export`（批量外流）仍保留管理权限，未放宽。

2. **越权返回空集而非 403**：`userId` 只能在范围内收窄；越权或不存在一律 `200 + total=0`。
   这样既不泄露「该用户是否存在」，也不会让正常操作突然失败。

3. **全量清理的审计保护**：分界取「**本次请求开始时刻**」而非 `now + 1`。
   `@OperationLog` 写入的审计日志 `create_time` 必然晚于该分界 → `create_time < cutoff` 不成立
   → **这条审计日志既不会被归档、也不会被这次清理自己删掉**。
   另加**保留期护栏**：按时间清理时必须保留 ≥1 天（`MIN_KEEP_DAYS`），
   否则「把截止时间设成 5 分钟前」等于变相擦除痕迹。

### 二、设计要点

- **为何不是纯 AOP 改写查询条件**：待拼装的 `LambdaQueryWrapper` 通常是方法内部局部变量，切面拿不到；强行实现只能退化为「SQL 拦截器隐式改写」，与本项目「不引入隐式行为」的约定冲突。故采用「注解 + AOP 准备上下文 + 业务侧一行显式 applyTo」，既统一又可见可调试。
- **数据权限的多角色口径**：取**最宽**（枚举 code 最小值）。理由：数据权限用于「让经理看到本部门」，一个用户同时是「部门经理」和「全体可见角色」时，应取更宽的那个，否则配置越多权限越小，违反直觉。

## 2026-10-01-02 逻辑删除唯一索引改造落地（路径 D：生成列 + NULL 语义，含 7 张表 DDL）



**改动类型**：数据库结构变更（DDL）+ 代码重构（移除应用层占位改写）+ 自检器判据升级

**原因**：用户「选择行业内最推荐的方案执行」。MySQL 无 PostgreSQL 的 partial unique index，业界通行替代手法是**生成列 + 复合唯一索引 + NULL 语义**（方案文档 v2 §1/§5）。



### 一、数据库变更（7 张表）



```sql

ALTER TABLE <t>

  ADD COLUMN active_flag TINYINT

      GENERATED ALWAYS AS (IF(is_deleted = 0, 1, NULL)) VIRTUAL

      COMMENT '仅供唯一索引使用：存活=1，已删=NULL（利用 MySQL 唯一索引允许多个 NULL）',

  DROP INDEX <uk_x>,

  ADD UNIQUE KEY <uk_x> (<编码列>, active_flag);

```



| 表 | 唯一索引 | 编码列 |

| --- | --- | --- |

| `oa_user` | `uk_username` | `username` |

| `oa_role` | `uk_role_code` | `role_code` |

| `oa_department` | `uk_dept_code` | `dept_code` |

| `oa_dict_type` | `uk_dict_type` | `dict_type` |

| `oa_flow_definition` | `uk_flow_code` | `flow_code` |

| `oa_company` | `uk_company_code` | `company_code` |

| `oa_meeting_room` | `uk_room_code` | `room_code` |



原理：存活行 `active_flag = 1` → 唯一索引按 `(编码, 1)` 约束，同编码只能有一条存活行；已删行 `active_flag = NULL` → MySQL 唯一索引允许多个 NULL，故任意多条已删行互不冲突。

- **现象**：`DELETE /system/login-log/clean`（不传 `before`）返回 `5000 系统内部错误`。服务层里明明有 `before == null` 校验，却成了死代码。

- **成因**：控制器用 `@RequestParam`（默认 `required = true`），参数缺失时 Spring 在**方法体执行前**就抛 `MissingServletRequestParameterException`；全局处理器没有对应分支，落进兜底 `Exception` → 5000。同类问题还有参数类型转换失败（如 `before=abc`）。另外 `ErrorCode` 里 `METHOD_NOT_ALLOWED(405)`、`NOT_FOUND(404)` 早已定义却从未被使用。

- **处置**：`GlobalExceptionHandler` 补 4 个分支——`MissingServletRequestParameterException`（`缺少必填参数: xxx`）、`MethodArgumentTypeMismatchException`（`参数格式不正确: xxx`）、`HttpRequestMethodNotSupportedException`（405）、`NoResourceFoundException`（404，不打堆栈）。

#### 缺陷 3（中）：`#{#before}` 未解析，日志里留下原始模板



- **现象**：`operation` 字段存的是字面量 `清理登录日志 #{#before}`，而同机制的 `发布公告 #{#id}` 却能正常解析成 `发布公告 1`。

- **定位**：写了一个隔离探针（`-parameters` 编译，直接调用 `MethodBasedEvaluationContext` + `TemplateParserContext`）复现，拿到确切原因：



  ```

  EL1001E: Type conversion problem, cannot convert from java.time.LocalDateTime to java.lang.String

  cause: ConverterNotFoundException: No converter found capable of converting from type

         [java.time.LocalDateTime] to type [java.lang.String]

  ```



  根因是 `resolveOperation` 里调用了 `.getValue(context, String.class)`，依赖 SpEL 默认的 `StandardTypeConverter`（底层 `DefaultConversionService`）。它只认显式注册的类型转换器：`Long -> String` 能转，`LocalDateTime -> String` 转不了；异常被 catch 静默吞掉后回退成原始模板。**Bean 字节码中 `MethodParameters` 属性正常存在，参数名发现机制没有问题**，排除了「参数名缺失」这一常见猜测。

- **处置**：保留 `TemplateParserContext`，给求值上下文装一个宽松的 `TypeConverter`（`DefaultConversionService` + 显式 `Object -> String` 转换器，统一走 `String.valueOf`）；同时把 catch 里的静默吞异常改为 `log.debug`，便于日后定位注解写错这一类问题。

- **验证**：`清理登录日志 2000-01-01T00:00`、`清理操作日志 2000-01-01T00:00`、`发布公告 1`、`启用或停用部门 2`、`启用或停用菜单 82` 全部正确解析。

## 2026-09-29-06 修复：流程标识归一化 + 一致性自检（方案 A+B）



**改动类型**：缺陷修复（高危——发起流程会执行到别的模板）



### 成因回顾



引擎的流程定义 key 取自 BPMN 的 `<process id>`，发起流程走 `startProcessInstanceByKey`（按 key 取**最新版本**）。设计器新建画布的默认值是 `process_1`，多个模板共用同一 id 时后部署者顶掉先部署者。



### 方案 A：部署前统一归一化



- **新增 `workflow/util/BpmnXmlNormalizer.java`**：把 `<process id>` 改写为流程编码，并同步改写 `<bpmndi:BPMNPlane bpmnElement>` 对它的引用（不改会令 bpmn-js 重新打开时画布空白）。幂等——process id 已等于目标值或找不到 `<process>` 时原样返回；序列化用 `Transformer`，开启 `FEATURE_SECURE_PROCESSING` 并置空外部 DTD/样式表访问。

- **`workflow/util/BpmnXmlParser.java`**：`NS_BPMN` 与 `parseDocument` 由 `private` 放宽为包级可见，让归一化器复用同一套 XXE 加固配置（各自 new 一个 `DocumentBuilderFactory` 极易漏配加固项）。

- **`FlowDefinitionServiceImpl.deployAndBind`**：部署前先 `overrideProcessId(xml, fd.getFlowCode())`，用归一化后的 XML 部署与解析 key。



### 方案 B：兜底校验 + 启动自检



- **`FlowDefinitionServiceImpl.assertBpmnKeyAvailable`**：保存前查该 `bpmn_key` 是否已被**其他** `flow_code` 占用，占用即抛 `FLOW_KEY_CONFLICT`。`flowCode` 唯一性校验在其之前，此处专门拦存量脏数据与未来新增部署入口。

- **新增 `workflow/bootstrap/FlowKeyConsistencyChecker.java`**：启动扫描 `oa_flow_definition`，把「bpmn_key 重复」与「bpmn_key ≠ flow_code」的模板打到 WARN 日志并给处置建议。**只读不改**——批量改写标识会牵动 Flowable 部署，须人工确认。归一化只对**新保存**的模板生效，历史数据靠它暴露。

- **`FlowBootstrapRunner`** 加 `@Order(100)`，与 Checker 的 `@Order(200)` 拉开顺序，保证本次播种的模板也纳入体检。

- **`common/ErrorCode.java`**：新增 `FLOW_KEY_CONFLICT(3006, "流程标识已被其他流程模板占用")`。

**标准启动方式**（推荐，命令行长度无风险）：



```bash

java -Dfile.encoding=UTF-8 -cp "target/classes;target/lib/*" com.kellen.oa_system.OaSystemApplication --server.port=8080

```



其中 `target/lib` 由 `mvnw.cmd dependency:copy-dependencies -DoutputDirectory=target/lib -DincludeScope=runtime` 生成（实测 79 个 jar，mysql 驱动与 spring-security 均在内；与 build-classpath 的 114 项差异全部是 test 作用域，运行时不需要）。



**实测验证**：8080 监听成功，`POST /auth/login` 返回 200 + JWT；无令牌访问 `/auth/info` 返回 401。



### 本轮踩到的 3 个坑（均已修复）



1. **Java 参数文件中 `--server.port` 必须放在主类名之后**。写在前会被当作 JVM 选项，直接报 `Unrecognized option` 并退出（表现为进程存在但端口不监听、日志为空）。

2. **Bash 命令里的 Windows 反斜杠会被转义破坏**（`C:\Users` → `C:\Uses\qiaz`）。生成 classpath 时统一改用正斜杠，Java 在 Windows 上完全支持。

3. **`.cmd` 脚本必须纯 ASCII**。cmd.exe 按 GBK 解析，UTF-8 中文注释会被当成命令执行导致脚本崩溃（日志表现为成片的乱码"不是内部或外部命令"）。脚本内注释已全部改为英文。



### 环境注意事项



- 本会话终端注入了 `SERVER__PORT` 环境变量，Spring Boot 松散绑定会覆盖配置文件的 `server.port`，启动时应显式带 `--server.port=8080`。

- 终端存在 HTTP 代理，curl 访问 127.0.0.1 必须加 `--noproxy "*"`，否则返回 502。

- 停止服务：`taskkill //F //PID <java_pid>`（勿用 `//IM java.exe` 全局清理，会误杀正在运行的服务实例）。

## 2026-09-28-04 引入 MyBatis-Plus + JWT + Validation 依赖



- **文件**：`pom.xml`

- **选型**：`mybatis-plus-spring-boot4-starter` 3.5.17（Boot 4 适配版）、jjwt 0.12.6（api/impl/jackson）、`spring-boot-starter-validation`



**踩坑（两个都是 Spring Boot 4 / MP 新版特有的）**：



1. **分页插件不在 classpath**。`mybatis-plus` 聚合包不传递 extension，且 3.5.16 起依赖 jsqlparser 的拦截器（含 `PaginationInnerInterceptor`）被拆到 **`mybatis-plus-jsqlparser-4.9`** 模块并标记为 optional。缺它时编译报「找不到符号 PaginationInnerInterceptor」。需同时显式引入 `mybatis-plus-extension` 与 `mybatis-plus-jsqlparser-4.9`。

## 2026-09-28-02 接入数据源（MySQL）



- **类型**：新增 + 修复

- **文件**：

  - `oa-system/pom.xml` — 新增 `spring-boot-starter-jdbc`

**为什么必须加 starter-jdbc**：项目为 Spring Boot **4.1.1**，该版本已把 JDBC 自动配置拆到独立模块 `spring-boot-jdbc`。只有 mysql-connector-j 而无此 starter 时，`spring.datasource.*` 不会生效，不会产生任何 DataSource Bean。



**踩坑记录**：



1. JDBC URL 不能写 `characterEncoding=utf8mb4` —— Connector/J 9.x 会抛 `Unsupported character encoding 'utf8mb4'`（Java 侧字符集名只有 `UTF-8`）。驱动默认即 utf8mb4，直接省略。

4. Java 17/21 才是主流 LTS；25 会让每次运行都需手动切 JDK
