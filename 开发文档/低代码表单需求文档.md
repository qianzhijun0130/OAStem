## 一、背景

审批中心的流程模板（`oa_flow_definition`）已有 `form_fields` 字段用于描述「发起申请要填哪些内容」，但存在三个实际问题：

1. **字段描述能力弱**。原字段格式仅支持 `text / textarea / number / date / select` 五种类型，由前端在 `views/workflow/apply/index.vue` 里手写 `v-for` 渲染分支。新增一种控件就要改一次模板代码，字段一多则不可维护。
2. **两个内置模板的 `form_fields` 均为 NULL**（`leave` / `expense`），导致发起页的「申请内容」区渲染为空——用户只能提交 `formData="{}"`，等于表单功能形同虚设。
3. **表单无法复用**。表单定义寄生在流程模板上，同一份「费用申请」若被两个流程使用就得复制两份规则，改一处漏一处。

FormCreate 是国内成熟的开源低代码表单方案（MIT 协议），提供**可视化设计器**（拖拽生成规则）与**运行时渲染器**（按规则渲染 + 内置校验）。本需求即以其替换原有手写渲染方案。

### 技术栈现状（实测）

| 项 | 版本 | 说明 |
| --- | --- | --- |

| UI 组件库 | Element Plus 2.14.6 | FormCreate 的 `element-ui` 适配包基于 Element Plus |
| 构建工具 | Vite 8.3.0 + TypeScript 6.0.2 | — |
| 后端 | Spring Boot 4.1.1 / Java 17 | JSON 处理用 **Jackson 3**（`tools.jackson`，非 `com.fasterxml.jackson`） |
| 数据库 | MySQL 8.0.46 | 需 ≥ 8.0.13（生成列 + 唯一索引多 NULL 语义） |

### 依赖选型说明

FormCreate 的设计器包存在**版本标签陷阱**，必须显式指定大版本：

| 包 | `latest` 标签 | `next` 标签 | 本项目采用 |
| --- | --- | --- | --- |
| `@form-create/designer` | 1.3.0（**Vue 2**，peer `vue: ^2.7.16`，依赖 `element-ui`） | 3.5.0（Vue 3，peer `vue: ^3.5`） | **3.5.0** |

## 二、功能需求

### 2.1 表单定义管理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 支持表单的增删改查、启用/停用 | 高 |
| FR-2 | 提供可视化设计器，支持拖拽生成表单规则 | 高 |
| FR-3 | 设计器产出的规则可保存为 JSON 并回显再次编辑 | 高 |
| FR-4 | 表单支持「复用已有表单」：载入一张已保存表单的规则作为设计起点 | 高 |
| FR-5 | 表单列表展示被引用次数，删除被引用表单时给出明确拒绝 | 中 |
| FR-6 | 表单编码软删除后可立即复用 | 中 |

### 2.2 流程表单绑定

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-7 | 可为流程的**任意节点**绑定表单（含发起环节） | 高 |
| FR-8 | 同一流程同一节点只能绑一个表单（重绑即覆盖） | 高 |
| FR-9 | 同一流程只允许一个「发起环节主表单」 | 中 |
| FR-10 | 发起页按绑定的主表单动态渲染并校验 | 高 |
| FR-11 | 审批详情页按规则只读回显已提交的表单数据 | 高 |

### 2.3 明确不做（范围外）

- 表单版本管理（规则改版不影响历史单据的展示快照）
- 流程表单的**跨节点分段填写**（当前只实现发起环节主表单的填写与展示；节点级填写需后续迭代）
- 表单的导入/导出与模板市场

## 三、交互流程

### 3.1 表单创建（可视化设计）

```
系统管理 → 表单管理 → 点「新增表单」
  ├─ 填写编码 / 名称 / 分类（Element 表单，编码格式前端正则校验）
  ├─ 「复用已有」下拉选一张已有表单
  │     └─ 载入其规则到设计器，编码/名称自动加 "_copy" 后缀（避免撞唯一索引）
  └─ 点「保存」
        └─ 后端校验 ruleJson 是 JSON 数组 → 派生 fieldSchema → 入库
```

设计器区域使用 FormCreate 官方 `<fc-designer>`：左侧组件面板拖拽、右侧属性配置、底部实时预览。

### 3.2 表单绑定到流程节点

```
审批中心 → 流程模板 → 选中某流程 → 绑定表单
  ├─ 选择节点（下拉，含「发起申请」）
  ├─ 选择表单（下拉，取自 /system/form/options，仅启用态）
  └─ 提交 → 后端「先逻辑删除旧绑定，再插新绑定」（全量覆盖语义）
```

### 3.3 发起申请（运行时）

```
发起申请 → 选流程模板
  └─ 触发 watch：GET /workflow/flow-definition/primary-form?flowCode=xxx
        ├─ 返回规则 → FormRender 渲染 + 接管校验
        └─ 返回 null → 显示提示「该流程未绑定表单」，降级为不渲染表单区
  └─ 点「提交申请」
        ├─ FormRender.validate() 触发 required / min / max / pattern 及自定义 validator
        ├─ 校验不通过 → 提示「请完善表单必填项」，不提交
        └─ 校验通过 → JSON.stringify(值) 存入 oa_approval_instance.form_data
```

### 3.4 审批详情（只读回显）

```
打开审批详情 → 取 form_data + 取主表单规则
  ├─ 有规则 → FormRender disabled 模式渲染（字段排版与填写时一致）
  ├─ 无规则但有数据 → 降级为键值对 el-descriptions（兼容未绑定表单的历史单据）
  └─ 两者皆无 → 「无表单数据」空态
```

## 四、数据模型

### 4.1 `oa_form`（表单定义表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK AUTO_INCREMENT | — |
| `form_code` | VARCHAR(64) NOT NULL | 表单编码，全局唯一 |
| `form_name` | VARCHAR(100) NOT NULL | 表单名称 |
| `category` | VARCHAR(32) | 分类 |
| `rule_json` | LONGTEXT NOT NULL | FormCreate 规则 JSON（option 数组） |
| `field_schema` | LONGTEXT | 字段清单 JSON（后端从 `rule_json` 派生） |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1启用 0停用 |
| `remark` | VARCHAR(255) | 备注 |
| `create_by/update_by` | BIGINT | 操作人 |
| `create_time/update_time` | DATETIME | 由 `FillMetaObjectHandler` 自动填充 |
| `is_deleted` | TINYINT NOT NULL DEFAULT 0 | 逻辑删除 |
| `active_flag` | TINYINT GENERATED VIRTUAL | `IF(is_deleted=0, 1, NULL)` |

**唯一索引**：`uk_form_code (form_code, active_flag)` —— 走项目既定的**路径 D**：靠「唯一索引允许多个 NULL」让已删行让位，故**业务值永不改写、编码删除后立即可复用**。

### 4.2 `oa_flow_node_form`（节点表单绑定表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | — |
| `flow_def_id` | BIGINT NOT NULL | 关联 `oa_flow_definition.id` |
| `node_key` | VARCHAR(100) NOT NULL | BPMN taskDefinitionKey；发起环节统一用 `init` |
| `node_name` | VARCHAR(100) | 节点名称（冗余，便于列表展示） |
| `form_id` | BIGINT NOT NULL | 关联 `oa_form.id` |
| `is_primary` | TINYINT NOT NULL DEFAULT 1 | 1=发起环节主表单 |
| `sort` | INT NOT NULL DEFAULT 0 | 排序号 |
| `active_flag` | TINYINT GENERATED VIRTUAL | 同上 |

**唯一索引**：`uk_flow_node (flow_def_id, node_key, active_flag)`

### 4.3 关键设计决策

**决策 1：为什么用关联表而不改 `node_config`**

`node_config` 描述的是「**谁审批**」，表单描述的是「**填什么**」。两者生命周期不同：表单可能被多个流程复用，改版后需同步更新所有引用；若把 `formId` 塞进 `node_config`，会造成规则数据与审批人规则相互污染，且无法建立复用关系。代价是多一次 JOIN，收益是解耦与复用。

**决策 2：`rule_json` 原样存储，不做结构改写**

后端只做两件必要的事：① 校验是 JSON 数组；② 抽出 `prop/label/type/required` 组成 `field_schema`。不重写规则结构，保证「**设计器所见 = 运行时所得**」，避免"静默清洗"导致设计结果与运行结果不一致。

**决策 3：`field_schema` 由后端派生而非前端传入**

后端是唯一可信源。若由前端传入，恶意请求可伪造 `required` 清单让后端跳过必填校验；由后端从 `rule_json` 派生则无法绕过。

**决策 4：`form_data` 存储结构不变**

仍存 JSON 字符串到 `oa_approval_instance.form_data`，**向后兼容**已有历史单据（如实例 51 存的 `{}`），无需数据迁移。

## 五、接口清单

### 5.1 表单管理（`system:form:*`）

| 方法 | 路径 | 权限码 | 说明 |
| --- | --- | --- | --- |
| GET | `/system/form/page` | `system:form:query` | 分页列表 |
| GET | `/system/form/options` | `system:flow:form-bind` | 启用态选项（绑定下拉用） |
| GET | `/system/form/{id}` | `system:form:query` | 详情（含完整规则） |
| POST | `/system/form` | `system:form:add` | 新增/更新（带 id 为更新） |
| PUT | `/system/form/{id}/status` | `system:form:edit` | 启用/停用 |
| DELETE | `/system/form/{id}` | `system:form:delete` | 删除（被绑定时 2504） |

### 5.2 节点绑定（`system:flow:form-bind`）

| 方法 | 路径 | 权限码 | 说明 |
| --- | --- | --- | --- |
| GET | `/workflow/flow-definition/primary-form?flowCode=` | **`system:approval:apply`** | 发起页取主表单 |
| GET | `/workflow/flow-definition/{id}/node-forms` | `system:flow:form-bind` | 列某流程全部绑定 |
| POST | `/workflow/flow-definition/node-forms` | `system:flow:form-bind` | 绑定/重绑 |
| DELETE | `/workflow/flow-definition/node-forms/{bindId}` | `system:flow:form-bind` | 解除绑定 |

⚠️ **`primary-form` 的鉴权特意用 `system:approval:apply` 而非管理权限码**：发起审批是全体员工的日常动作，若沿用管理权限，专员/员工打开发起页就会 403、无法发起。这与既有的 `/flow-definition/options` 是同一设计考虑。

### 5.3 错误码（25xx 段新增）

| 码 | 含义 |
| --- | --- |
| 2501 | 表单不存在 |
| 2502 | 表单编码已存在 |
| 2503 | 表单规则格式非法，请使用设计器生成规则 |
| 2504 | 该表单已被流程节点绑定，无法删除 |
| 2505 | 待绑定的流程模板不存在 |

## 六、权限控制

| 权限码 | 授予角色 | 用途 |
| --- | --- | --- |
| `system:form:query` | SUPER_ADMIN | 表单列表 / 详情 |
| `system:form:add` | SUPER_ADMIN | 新增 / 保存 |
| `system:form:edit` | SUPER_ADMIN | 编辑 / 启停 |
| `system:form:delete` | SUPER_ADMIN | 删除 |
| `system:form:design` | SUPER_ADMIN | 打开设计器 |
| `system:form:preview` | SUPER_ADMIN | 预览 |
| `system:flow:form-bind` | SUPER_ADMIN | 节点绑表单（挂在流程模板页面下） |

**双层控制**：前端用 `v-permission` 控制按钮显隐，后端用 `@PreAuthorize` 控制接口。**前端隐藏不等于安全**——实测普通员工直接调 `/system/form/page` 仍被后端拦为 `code=403`。

**菜单与路由**：菜单 id 100（表单管理，`visible=1` 进侧边栏）、101（表单设计）/102（表单预览），`visible=0` 只用于路由跳转。本项目路由由 `oa_menu` 表动态生成，新增页面**必须同步插入菜单数据**，否则路由不生效。

## 八、使用与注意事项

1. **设计器包必须锁 3.x 大版本**。`@form-create/designer` 的 `latest` 标签指向 Vue 2 版本（1.3.0），直接安装会引入 `element-ui` 与 Element Plus 冲突。正确写法：`npm i @form-create/element-ui@3.3.5 @form-create/designer@3.5.0`。

2. **依赖安全提示**。`npm audit` 报 4 个 high 级别漏洞，全部由设计器传递引入（`wangeditor` 的 XSS、`source-map-js` 的 DoS）。设计器仅在管理端内部使用、且只处理管理员自己产出的规则 JSON，风险可控；如需消除可评估移除 `wangeditor` 组件。

3. **已发起的单据不会因新增绑定而回填**。候选人/表单绑定只在发起那一刻解析。给流程补绑表单后，**历史单据的详情页仍走降级路径**（键值对展示），这是设计如此，不是缺陷。

4. **内置模板的 `form_fields` 已补齐**。`leave` / `expense` 两个模板原先 `form_fields` 为 NULL，发起页表单区渲染为空；现已补齐并同步建立 `oa_form` 定义与节点绑定，两个模板均可正常发起。

5. **表单删除有保护**。被流程节点绑定的表单删除时返回 2504，前端也会禁用删除按钮并在「引用」列显示引用次数。
