# OA 系统部门角色体系优化说明

> **文档定位**：企业角色体系的**设计蓝图 + 落地状态说明**。
> 本文档区分两类内容：**已落地**（系统当前真实生效）与 **待建**（本期不实现，见第五节）。
> 最后核对：2026-10-04

结合真实企业的部门岗位设置与权责逻辑，对原有角色体系做如下调整：

1. **移除角色**：删除通用型的「部门管理员」角色，将部门管理权责下沉到各部门的经理岗，避免权责边界模糊。✅ **已执行**
2. **保留角色**：保留系统级「超级管理员」、全员基础角色「普通员工」，以及人事部、财务部已有的经理 / 专员角色。
3. **新增角色**：为技术部、市场部补全对应业务角色（经理岗 + 执行岗），匹配部门实际业务职责。✅ **已执行**
4. **权限规则**：所有员工默认拥有「普通员工」基础权限，业务角色为权限叠加。⚠️ **本条已按系统实际修订**，见第四节。

## 四、权限配置机制（按系统实际修订）

### 4.1 权限叠加机制 —— ⚠️ 原设计不成立，已改为「克隆 + 独立勾选」

**原表述**：「人事经理同时会叠加普通员工的基础权限，无需重复配置」。

**系统实际**：平台**没有角色继承 / 权限叠加机制**。`RoleServiceImpl#expandAncestors` 只补全**菜单的祖先目录**（勾选子菜单时自动补上父目录，否则子菜单挂不上菜单树），**不涉及任何角色间权限继承**。

用户拥有多个角色时，其 `perms` 是各角色菜单的并集 —— 但这是「一个人绑多个角色」，不是「一个角色自动包含另一个角色」。

**修订后的配置规范**：

1. 每个角色必须**独立完整勾选**「基础菜单 + 业务菜单」。漏勾基础菜单（工作台、我的公告等）时，接口返回成功但**侧边栏缺节点、页面点不开**。
2. 新建角色时，**使用「克隆菜单」功能**以成熟角色为基线，再按需增删 —— 避免漏勾。
   - 入口：角色管理列表 → 操作列 →「克隆菜单」
   - 接口：`POST /system/role/{id}/menus/clone`，入参 `{"sourceRoleId": 源角色ID}`
   - 语义：**全量覆盖**（目标角色原有菜单被清空后写入），不可撤销，需二次确认
   - 实现复用 `assignMenus`，与手工授权走同一条写入路径（含祖先补全、菜单存在性校验、超管保护）
3. 本次落地的 6 个业务角色均以基线克隆方式授权：

| 目标角色 | 基线角色 | 额外补充 |
| --- | --- | --- |
| `TECH_MANAGER` / `MARKET_MANAGER` | `DEPT_ADMIN`（已含部门管理） | — |
| `HR_MANAGER` | `HR` | ➕ 部门管理 5 项 |
| `FINANCE_MANAGER` | `FINANCE` | — |
| `TECH_ENGINEER` / `MARKET` | `EMPLOYEE` | — |

### 4.2 数据权限 —— ⚠️ 现有 3 档，无法表达文档中的复合范围

**系统的实际能力**：`oa_role.data_scope` 为**单选三档**，经 `@DataScope` 注解 + AOP 生效：

| 取值 | 语义 |
| --- | --- |
| `1` | 全部数据 |
| `2` | 本部门（部门表场景为「本部门 + 其全部下级部门」） |
| `3` | 仅本人 |

**多角色口径**：取**最宽**（枚举 code 最小值）；超管直接视为「全部数据」；无角色 / 角色停用时收敛为「仅本人」；用户无归属部门时**收敛为不可见**（恒假条件，不误放开）。

**已接入数据权限的接口**（截至 2026-10-04）：

| 接口 | 生效范围 |
| --- | --- |
| `GET /system/user/page` 用户列表 | ✅ 全部 3 档 |
| `GET /system/dept/tree` 部门树 | ✅ `全部` / `本部门（含下级）`；`仅本人` 收敛为仅本部门 |
| 部门 / 公告 / 流程模板 / 审批 / 文件 | ❌ 尚未接入 |

**文档中的复合数据范围如何落地**：

| 文档要求 | 现状 | 差距 |
| --- | --- | --- |
| 人事经理：本部门 + **全公司人事核心数据** | 近似为 `全部数据` | 缺少**字段级权限**（系统无「薪酬/绩效列不可见」这类机制） |
| 人事专员：本部门 + **全公司员工基础信息（无薪酬/绩效）** | 近似为 `本部门` | 同上，且无法表达「跨部门但字段受限」 |
| 财务专员：本部门 + **本人经办的财务数据** | 近似为 `本部门` | 需业务表具备「经办人」字段并接入 `@DataScope`（表结构待建） |
| 研发工程师：本部门 + **本人负责的模块** | 近似为 `本部门` | 同上 |

> **结论**：现有 3 档 + 单值语义**只能近似表达**文档要求。要做到「跨部门 + 字段级 + 按业务经办人」的精确控制，需要**字段级权限机制**与**业务表补齐归属字段（DDL）**，属后续独立迭代项。

### 4.3 角色类型字段

`oa_role.role_type` 仅有 `1 系统角色` / `2 业务角色` 两档（DTO 有 `@Min(1) @Max(2)` 校验），**不参与任何权限判定**，仅用于列表页标签展示。原文档中「系统基础角色」这一档在系统中无对应取值，普通员工统一归入 `1 系统角色`。

## 五、待建模块清单（本期不落地）

以下职责在系统内**尚无对应数据表与代码**，文档中的相关描述属**企业愿景**，不代表已交付能力：

| 待建项 | 现状核查结论 |
| --- | --- |
| **考勤** | `oa_attendance` 表存在，但**无后端代码、无前端页面**；无对应流程模板 |
| **薪酬 / 绩效** | 系统**无任何相关表或字段**；文档中「人事经理可见薪酬绩效」暂无法实现 |
| **客户 / 销售管理** | 系统**无客户、销售、线索相关表** |
| **请假 / 报销** | ⚠️ 部分可用：请假与报销**可**通过 Flowable 流程模板实现（内置 `leave` / `expense` 模板，审批中心已可用），但**无独立的业务表** |

| **报表导出** | 平台有通用 Excel 导出工具（`ExcelExportUtil`），但**各业务模块的导出接口尚未全部接入** |
| **字段级权限** | 系统无「按列隐藏 / 脱敏」机制，见 4.2 |

> 另一类「空壳表」：`oa_meeting`、`oa_task`、`oa_document`、`oa_schedule`、`oa_process_definition` 等 **13 张表**同样只有表结构、无后端代码与前端页面。

## 六、后续扩展规范

若后续新增部门（如运营部、销售部），按 **「经理岗 + 执行岗」** 统一逻辑扩展：

1. 新建经理岗 → 角色管理 →「克隆菜单」选一个同类经理岗为基线 → 补部门管理权限 → 裁剪
2. 新建执行岗 → 克隆 `EMPLOYEE` → 按需增加业务菜单
3. `data_scope` 建议：经理岗 = `2 本部门`，执行岗 = `2 本部门`（需要「仅本人经办」精确控制时，待业务表补齐经办人字段后再细化）
4. **不要**通过「给角色改名字」来表达岗位差异 —— 角色与部门是多对多关系，一个部门的管理者应绑定经理岗角色，而非为每个部门各建一个管理员角色。
