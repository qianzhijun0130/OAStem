# RuoYi Office 权限体系详解

> 文档类型：横切专题（权限体系）技术需求文档
> 覆盖范围：后端 `ruoyi-office-master-jdk17-开源`（yudao/RuoYi-Vue-Pro 定制）+ 前端 `ruoyi-office-vben-master-开源`
> 内容：角色定义、权限分类、访问控制机制、关键模块权限分配逻辑、边界规则，按"网关→数据"五层 + 前端分层级呈现。

## 0. 全景：权限体系五层架构

权限控制自外向内分为 **5 层**，每一层解决不同粒度的问题，且逐层收紧：

```
┌─ 第①层 认证与令牌 ──────────────────────────────────────────┐
│  网关 TokenAuthenticationFilter → 服务端 TokenAuthenticationFilter  │
│  解决"你是谁"：校验 accessToken，透传 LoginUser；匿名接口 @PermitAll     │
├─ 第②层 接口级功能权限（RBAC）───────────────────────────────┤
│  @PreAuthorize("@ss.hasPermission('system:user:create')")             │
│  解决"你能调用哪些接口/看到哪些按钮"：用户-角色-菜单(权限标识)             │
├─ 第③层 数据权限（行级）──────────────────────────────────────┤
│  @DataPermission + DataPermissionInterceptor → 拼 dept_id/user_id      │
│  解决"同一接口下你能看到哪些数据行"：部门数据范围 ALL/CUSTOM/ONLY/...     │
├─ 第④层 业务行级权限 ─────────────────────────────────────────┤
│  CRM @CrmPermission(OWNER/WRITE/READ) ｜ BPM 候选人策略(16 种)          │
│  解决"这条业务记录你能不能操作"：按数据归属人/角色/部门/表达式              │
├─ 第⑤层 多租户隔离 ───────────────────────────────────────────┤
│  TenantLineInnerInterceptor → 拼 tenant_id = ?                        │
│  解决"数据属于哪个租户"：所有 SQL 强制租户条件                            │
└──────────────────────────────────────────────────────────────┘
            ▲ 前端对应链路：登录→get-permission-info→动态菜单/路由→v-access→请求头
```

### 过滤器链顺序（`WebFilterOrderEnum.java:12-36`，越靠前越先执行）

| 顺序 | 过滤器 | 职责 |
|---|---|---|
| Integer.MIN_VALUE | CORS_FILTER | 跨域 |
| +1 | TRACE / ENV_TAG_FILTER | 链路追踪 / 环境标签 |
| MIN+500 | REQUEST_BODY_CACHE / API_ENCRYPT_FILTER | 请求体缓存 / API 加解密 |
| **-104** | **TENANT_CONTEXT_FILTER**（`TenantContextWebFilter`） | 解析 `tenant-id` → `TenantContextHolder` |
| -103 | API_ACCESS_LOG_FILTER | 接口访问日志 |
| -102 | XSS_FILTER | XSS 过滤 |
| **-100** | **Security FilterChain**（含 `TokenAuthenticationFilter`，注册于 `UsernamePasswordAuthenticationFilter` 前，`YudaoWebSecurityConfigurerAdapter.java:151`） | 认证 + URL 级授权 |
| **-99** | **TENANT_SECURITY_FILTER**（`TenantSecurityWebFilter`） | 租户越权 / 合法性校验 |
| -98 | FLOWABLE_FILTER | 工作流上下文 |

> 顺序要点：租户上下文(-104)先于认证(-100)先于租户安全(-99)，保证认证时可读取租户、越权拦截在业务前完成。

## 1. 角色定义

### 1.1 角色数据模型（`system_role`）

| 字段 | 说明 |
|------|------|
| `id` | 主键 |
| `name` | 角色名称 |
| `code` | 角色编码（唯一，如 `super_admin`、`tenant_admin`、`crm_admin`） |
| `type` | 角色类型：`RoleTypeEnum` = SYSTEM(1 内置) / CUSTOM(2 自定义) |
| `data_scope` | 数据范围：`DataScopeEnum` 五档（见第 3 节） |
| `data_scope_dept_ids` | 自定义数据范围对应的部门 ID 集合（`JacksonTypeHandler` 存取 `Set<Long>`） |
| `sort` / `status` | 排序 / 状态 |
| `tenant_id` | 所属租户（继承 `TenantBaseDO`） |

`RoleDO`：`yudao-module-system-server/.../dal/dataobject/permission/RoleDO.java:26-77`。

### 1.2 内置角色与保护规则

`RoleCodeEnum`（`system-api/.../enums/permission/RoleCodeEnum.java:14-30`）：

| 编码 | 语义 | 说明 |
|------|------|------|
| `super_admin` | 超级管理员 | `isSuperAdmin()` 只认此码，享有框架级全权限（三处放行点，见第 9 节） |
| `tenant_admin` | 租户管理员 | 租户维度管理语义 |
| `crm_admin` | CRM 管理员 | 仅 CRM 模块 `@CrmPermission` 中直接放行（`CrmPermissionUtils.isCrmAdmin()`） |

**保护规则**（`RoleServiceImpl.java`）：
- `validateRoleDuplicate` L148-152：禁止创建 `code=super_admin` 的角色。
- `validateRoleForUpdate` L175-185：`type=SYSTEM` 内置角色不可改/删。
- `createRole` L66：新角色默认 `dataScope = ALL`（注释：部分项目不需要数据权限）。

## 2. 权限分类

项目存在 **5 类权限**，粒度由粗到细：

| 类别 | 载体 | 判定机制 | 影响范围 |
|------|------|----------|----------|
| **功能权限**（接口/按钮） | `system_menu.permission`，格式 `${系统}:${模块}:${操作}`，如 `system:user:create` | `@PreAuthorize("@ss.hasPermission(...)")` + 前端 `v-access:code` | 能否调用接口 / 按钮是否显示 |
| **数据权限**（行级） | `system_role.data_scope` + `data_scope_dept_ids` | `@DataPermission` → `DeptDataPermissionRule` 拼 SQL | 接口返回哪些数据行 |
| **业务行级权限** | CRM `crm_permission` 表 / BPM 流程节点策略 | `@CrmPermission` 切面 / `BpmTaskCandidateInvoker` | 单条业务记录能否操作 |
| **租户隔离** | 所有表 `tenant_id` | `TenantLineInnerInterceptor` 拼 `tenant_id = ?` | 数据归属哪个租户 |
| **菜单/路由权限** | `system_menu`（type=目录/菜单/按钮） | 后端菜单 → 前端动态路由 + 菜单 | 能看到并进入哪些页面 |

### 菜单即资源（`MenuDO` / `system_menu`）

- `MenuTypeEnum`：DIR(1 目录) / MENU(2 菜单) / BUTTON(3 按钮)。
- `MenuDO`（`MenuDO.java:23`）类上标 `@TenantIgnore` —— **菜单全局共享，不按租户隔离**。
- `permission` 字段注释（`MenuDO.java:41-48`）：授予角色即代表拥有该资源，后端配 `@PreAuthorize`、前端配按钮标签。
- 树形结构：`parent_id`；字段 `component` / `path` / `visible` / `keepAlive` / `sort` 驱动前端路由。

### RBAC 五张核心表（`sql/mysql/ruoyi-vue-pro.sql`）

| 表 | 行号 | 用途 |
|----|------|------|
| `system_users` | L3967 | 管理员用户（`dept_id` 冗余，供数据权限使用） |
| `system_role` | L2663-2680 | 角色 |
| `system_menu` | L1381-1402 | 菜单/权限资源 |
| `system_user_role` | L3923 | 用户-角色 |
| `system_role_menu` | L2698-2709 | 角色-菜单 |

## 3. 第②层：接口级功能权限（RBAC）

### 3.1 权限判定算法（`PermissionServiceImpl.java`）

**`hasAnyPermissions(userId, permissions)`（L62-84）**：
1. `permissions` 为空 → 直接 `true`（L65-67）；
2. `getEnableUserRoleIdListByUserIdFromCache(userId)`（L259-266）：读用户角色缓存 → 角色缓存 → 过滤禁用角色；无角色 → `false`；
3. 对每个 `permission` 调 `hasAnyPermission(roles, permission)`（L93-111）：
   - `menuService.getMenuIdListByPermissionFromCache(permission)`（`@Cacheable(permission_menu_ids)`）；
   - **严格模式**：`permission` 在 `system_menu` 中找不到即无权限（L95-98 注释）；
   - 对每个 `menuId` 取 `getMenuRoleIdListByMenuIdFromCache(menuId)`（`@Cacheable(menu_role_ids)`），与用户角色集合求交集，有交集即有权限；
4. 兜底：`roleService.hasAnySuperAdmin(roleIds)` —— 超管直接放行（L83）。

**`hasAnyRoles(userId, roles)`（L113-129）**：比对 `RoleDO.getCode()` 集合交集（用 code 而非 id）。

**`getDeptDataPermission(userId)`（L275-330）**（数据权限数据来源，见第 4 节）：方法上 `@DataPermission(enable=false)` 防递归；遍历用户启用角色按五档累加；无任何角色 → 仅自己。

### 3.2 缓存体系与失效（`RedisKeyConstants.java`）

| Key | 内容 |
|-----|------|
| `role:{id}` | 角色 |
| `user_role_ids:{userId}` | 用户角色 ID |
| `menu_role_ids:{menuId}` | 菜单→角色 |
| `permission_menu_ids:{permission}` | 权限标识→菜单 |
| `dept_children_ids:{id}` | 部门子部门树 |

失效策略（多为粗粒度 allEntries 全清，`PermissionServiceImpl.java`）：`assignRoleMenu` 清 `menu_role_ids`+`permission_menu_ids` 全量；`processRoleDeleted` 清 `menu_role_ids`+`user_role_ids` 全量；`processMenuDeleted` 按 `#menuId` 清；`assignUserRole`/`processUserDeleted` 按 `#userId` 清 `user_role_ids`。

### 3.3 `@ss` SpEL 机制（功能权限入口）

- 注册（`YudaoSecurityAutoConfiguration.java:76-79`）：`@Bean("ss")` → `SecurityFrameworkServiceImpl`。
- 方法安全：`YudaoWebSecurityConfigurerAdapter.java:48` `@EnableMethodSecurity(securedEnabled=true)`。
- 解析链：`@PreAuthorize("@ss.hasPermission('system:user:create')")` → `SecurityFrameworkServiceImpl.hasPermission`（`SecurityFrameworkServiceImpl.java:60-62`）→ `hasAnyPermissions`（L64-78）：
  1. `skipPermissionCheck()` 为 true（跨租户访问）→ 直接 true；
  2. `getLoginUserId()` 为 null → false；
  3. Guava `LoadingCache`（L48-57，1 分钟 `refreshAfterWrite`）→ `permissionApi.hasAnyPermissions(...)`。

### 3.4 URL 级授权规则组装（`YudaoWebSecurityConfigurerAdapter.filterChain` L109-153）

1. 静态资源 + `getPermitAllUrlsFromAnnotations()`（L159-219：扫描 `RequestMappingHandlerMapping`，方法级/类级 `@PermitAll` 均收录）+ `securityProperties.getPermitAllUrls()`；
2. 各模块 `AuthorizeRequestsCustomizer`（`security/config/AuthorizeRequestsCustomizer.java`，提供 admin-api/app-api 前缀拼接）；
3. 兜底：`ASYNC` permitAll（SSE 场景）+ `anyRequest().authenticated()`。

### 3.5 注解用法统计（全仓实测）

- `@PreAuthorize`：**1257 处**（覆盖 system/bpm/crm/oa/ai/member/mp/erp/mall/pay/hrm/asset/report/infra/iot/wms）。
- `@PermitAll`：41 处；`@TenantIgnore`：32 处；`@DataPermission`：24 处（bpm 16、system 8）。
- `@ss.hasPermission` 绝对主流；`@ss.hasAnyRoles/hasRole` 业务未用；`@ss.hasScope` 仅 4 处（`OAuth2UserController` 的 `user.read`/`user.write`，供外部 OAuth2 应用）。

典型控制器：`UserController`(`system:user:create/update/delete/update-password/query`)、`PermissionController`(`system:permission:assign-role-menu/assign-role-data-scope/assign-user-role`)、`CrmCustomerController`(`crm:customer:create/update/delete/query`)、`BpmProcessInstanceController`(`bpm:process-instance:query/manager-query/cancel/...`)。

## 4. 第③层：数据权限（行级）

### 4.1 注解与 AOP

- `@DataPermission`（`biz-data-permission/.../core/annotation/DataPermission.java:16-34`）：`enable()`、`includeRules()`、`excludeRules()`（include 优先），可标类/方法。
- Advisor：`DataPermissionAnnotationAdvisor.java:31-33`（类 + 方法双切点）。
- Interceptor：`DataPermissionAnnotationInterceptor.java:33-48`：方法前 `DataPermissionContextHolder.add`、finally `remove`；按 `MethodClassKey` 缓存。
- 上下文：`DataPermissionContextHolder`：`TransmittableThreadLocal<LinkedList<DataPermission>>`，`get()` 取 `peekLast()`（支持嵌套）。

### 4.2 数据范围五档（`DataScopeEnum`）

| 档位 | 含义 | `getDeptDataPermission` 处理 |
|------|------|------------------------------|
| `ALL` | 全部数据 | `result.setAll(true)` |
| `DEPT_CUSTOM` | 自定义部门 | 累加 `dataScopeDeptIds`，**并追加本人所在部门**（L304-306，否则按 username 登录查询会被 dept_id 过滤掉） |
| `DEPT_ONLY` | 仅本部门 | 累加本人部门 |
| `DEPT_AND_CHILD` | 本部门及子部门 | 累加 `getChildDeptIdListFromCache(本人部门)` + 本人部门 |
| `SELF` | 仅本人 | `result.setSelf(true)` |
| （无角色） | — | 仅自己（L283-286） |

### 4.3 SQL 拦截与条件拼接

- 装配：`YudaoDataPermissionAutoConfiguration.java:29-39`：`DataPermissionInterceptor` 装入 `MybatisPlusInterceptor` **首位**（须在分页插件前）。
- Handler：`DataPermissionRuleHandler.java:31-62`：`skipPermissionCheck()` → null；按 `mappedStatementId` 取规则 + 表名匹配；多规则用 `AndExpression` 串联。
- 部门规则：`DeptDataPermissionRule.java:89-173`：
  - `loginUser == null` 或 `userType != ADMIN` → **不拼接**（会员端无部门数据权限，L91-98）；
  - `DeptDataPermissionRespDTO` 缓存在 `LoginUser.context`（CONTEXT_KEY，避免每次 SQL 都 RPC）；
  - `all=true` → null（不过滤）；
  - 无部门且不可看自己 → `new EqualsTo(null, null)`（`WHERE null = null` 保证查不出数据，L122）；
  - 最终条件：`(dept_id IN (...) OR user_id = ?)`（L143，`ParenthesedExpressionList(OrExpression)`）；仅 SELF 时 `user_id = 当前用户`。
  - 表-字段映射由 `addDeptColumn/addUserColumn` 注册（system 注册 `AdminUserDO.dept_id`(dept)/`AdminUserDO.id`(user)/`DeptDO.id`(dept)，见 `DataPermissionConfiguration.java:18-26`）。
- 代码级忽略：`DataPermissionUtils.executeIgnore(Runnable/Callable)`（`AdminUserServiceImpl.java:388` 等使用）。
- RPC 透传：`DataPermissionRequestInterceptor` 带 `data-permission-enable:false` 头，对端 `DataPermissionRpcWebFilter` 读取后包 `executeIgnore`。
- 规则工厂优先级（`DataPermissionRuleFactoryImpl.java:34-65`）：无规则→空；**无注解→默认全量规则生效**；`enable=false`→空；easy-trans 翻译调用→空；include/exclude 过滤。

## 5. 第④层：业务行级权限

### 5.1 CRM：`@CrmPermission`（OWNER/WRITE/READ）

- 注解：`crm-server/.../framework/permission/core/annotations/CrmPermission.java:22-45`：`bizType`、`bizTypeValue`（SpEL）、`bizId`（SpEL，支持集合）、`level`。
- 级别：`CrmPermissionLevelEnum.java:22-24`：`OWNER(1 负责人) > READ(2 只读) > WRITE(3 读写)`。
- 切面：`CrmPermissionAspect.java:46-111`（`@Before`）：
  1. 解析 bizId/bizType（`SpringExpressionUtils`，bizId 支持 Collection 批量）；
  2. `crmPermissionService.getPermissionListByBiz` 读 `crm_permission` 表（biz_type/biz_id/user_id/level）；
  3. `validatePermission` 顺序：`isCrmAdmin()`（`crm_admin`）→ 直接通过；无记录：READ 放行（公海人人可读）；有记录无负责人：READ 放行；自身权限（OWNER 全通过 / READ 需 READ/WRITE / WRITE 需 WRITE）；**下级权限**：`adminUserApi.getUserListBySubordinate(userId)` 递归校验下属；失败抛 `CRM_PERMISSION_DENIED` 并打审计日志。
- 典型用法：`CrmCustomerServiceImpl` 的 update(WRITE, L128)/delete(OWNER, L185)/transfer(OWNER, L205)/lock(OWNER, L254)/putPool(OWNER, L366)/get(READ, L483)。
- 查询侧过滤：`CrmPermissionUtils.appendPermissionCondition`（L48-77）："我负责的"`owner_user_id=userId`；"我参与的"innerJoin `crm_permission`；"下属负责的"`owner_user_id in 下属ids`（无下属用 `-1` 防空）。

### 5.2 BPM：候选人/审批人策略（16 种）

- 调用器：`BpmTaskCandidateInvoker.java`：`validateBpmnConfig`（L57-83）部署前校验每个 UserTask 已配置策略与参数（跳过 AUTO_APPROVE/AUTO_REJECT，未配置抛 `MODEL_DEPLOY_FAIL_TASK_CANDIDATE_NOT_CONFIG`）；`calculateUsersByTask`（L92-126，`@DataPermission(enable=false)` + `FlowableUtils.execute(tenantId)`）→ 计算 → `removeDisableUsers` → 空走 `ASSIGN_EMPTY` → `removeStartUserIfSkip`（候选>1 且配置"审批人与发起人相同则跳过"时移除发起人）。
- 策略枚举：`BpmTaskCandidateStrategyEnum.java:21-36`（16 种）：`ASSIGN_EMPTY(1)`、`ROLE(10)`、`DEPT_MEMBER(20)`、`DEPT_LEADER(21)`、`POST(22)`、`MULTI_DEPT_LEADER_MULTI(23)`、`USER(30)`、`APPROVE_USER_SELECT(34)`、`START_USER_SELECT(35)`、`START_USER(36)`、`START_USER_DEPT_LEADER(37)`、`START_USER_DEPT_LEADER_MULTI(38)`、`USER_GROUP(40)`、`FORM_USER(50)`、`FORM_DEPT_LEADER(51)`、`EXPRESSION(60)`。
- 实现：`candidate/strategy/{user,dept,form,other}/`，如 `BpmTaskCandidateRoleStrategy.java:38-41` 调 `permissionApi.getUserRoleIdListByRoleIds`。
- BPM 的 16 处 `@DataPermission(enable=false)` 集中在 `BpmTaskServiceImpl`/`BpmProcessInstanceServiceImpl`（否则数据权限会过滤掉候选人）。

## 6. 第⑤层：多租户隔离

### 6.1 tenant-id 透传链
1. `WebFrameworkUtils.java:30-31,53-56`：header `tenant-id` / `visit-tenant-id`（`getTenantId` 仅接受纯数字）。
2. `TenantContextWebFilter`（-104）：写入 `TenantContextHolder`（`TransmittableThreadLocal`），finally `clear()`。
3. DB 层：`TenantLineInnerInterceptor` + `TenantDatabaseInterceptor.java:41-81`：所有 SQL 拼 `tenant_id = ?`；`ignoreTable` 三级判断（全局 ignore → 继承 `TenantBaseDO` 不忽略 → 类上 `@TenantIgnore` 忽略 → 非 yudao 表忽略）。
4. 装配：`YudaoTenantAutoConfiguration.java:85-93`（拦截器首位）、`97-103`（Filter）。

### 6.2 TenantSecurityWebFilter（越权防护，-99，`TenantSecurityWebFilter.java:65-111`）
1. 已登录：未传 tenantId 用登录用户租户；**传了且与 `user.getTenantId()` 不一致 → 403"您无权访问该租户的数据"**（L76-83）；
2. 非 ignoreUrl 且无 tenantId → 400"请求的租户标识未传递"；
3. `tenantFrameworkService.validTenant(tenantId)` 校验租户禁用/到期；
4. ignoreUrl 且无 tenantId → `setIgnore(true)`。
- ignoreUrl 双来源：`TenantProperties.ignoreUrls` + 扫描 `@TenantIgnore` 自动收集（`YudaoTenantAutoConfiguration.java:143-166`）。

### 6.3 `@TenantIgnore`（`TenantIgnore.java:20-32`，支持 SpEL `enable()`）
- 标 Controller → URL 进 ignoreUrls；标 DO → 表进 ignoreTables（如 `MenuDO`/`system_menu` 全局共享）。
- 典型：`TenantController` 的 `/get-id-by-name`、`/simple-list`、`/get-by-website`（均 `@TenantIgnore`）；`/admin-api/mp/open/**`（yaml `permit-all-urls`）。

### 6.4 跨租户访问与权限跳过（高风险，需严控）
- `TenantVisitContextInterceptor.java:30-54`：header `visit-tenant-id` 与当前租户不同时，要求权限 **`system:tenant:visit`**（L23,46-48），随后 `loginUser.setVisitTenantId(...)` 并切换 `TenantContextHolder`。
- 由此触发框架级放行：`SecurityFrameworkUtils.skipPermissionCheck()`（`SecurityFrameworkUtils.java:150-160`）——`visitTenantId != tenantId` 时返回 true，**同时跳过 `@ss` 功能权限与 `dept_id` 数据权限**（`SecurityFrameworkServiceImpl.java:68,89,109`、`DataPermissionRuleHandler.java:33`）。

## 7. 前端权限体系

### 7.1 登录与权限信息获取（链路）
```
loginApi (POST /system/auth/login, isEncrypt:false)
  → { accessToken, refreshToken, userId, expiresTime }
  → accessStore.setAccessToken/setRefreshToken
  → fetchUserInfo() → getAuthPermissionInfoApi (GET /system/auth/get-permission-info)
      → AuthPermissionInfo { user, roles, permissions, menus }
          ├─ userStore.setUserInfo(user) / setUserRoles(roles)
          ├─ accessStore.setAccessMenus(menus)          // 后端菜单树 AppRouteRecordRaw[]
          └─ accessStore.setAccessCodes(permissions)    // 权限码 string[]
```
- `api/core/auth.ts`：`loginApi`(L66-72)、`refreshTokenApi`(L75-79，走 `baseRequestClient` 不带 Authorization)、`logoutApi`(L82-92)、`getAuthPermissionInfoApi`(L95-99)。
- 类型 `AuthPermissionInfo`：`packages/types/src/user.ts`。
- `useAuthStore.fetchUserInfo`（`store/auth.ts` L133-144）是权限分发核心。
- `useAccessStore`（`packages/stores/src/modules/access.ts`）：`persist.pick` 持久化 `accessToken/refreshToken/accessCodes/tenantId/visitTenantId`，**不持久化 `accessMenus/accessRoutes/isAccessChecked`**（刷新后需重新生成路由）。

### 7.2 accessMode：项目实际为 `backend`
- 默认 `frontend`（`@core/preferences/src/config.ts` L5），**应用覆盖为 `backend`**（`apps/web-antd/src/preferences.ts` L12，web-ele 同）。
- `backend` 模式（`generateRoutesByBackend`）：读 `accessStore.accessMenus` → `convertServerMenuToRouteRecordStringComponent`（外链→IFrameView、`parentId=0`且有子→BasicLayout、`component='Layout'`→BasicLayout、`visible→hideInMenu`、name 去重）→ 与前端静态 `accessRoutes` 合并 → `router.addRoute` 挂到 `Root.children`。
- `frontend` 模式则用前端静态路由 `meta.authority` 与 `roles` 求交集过滤。**结论：菜单/路由权限由后端 `menus` 决定**，前端 `routes/modules/*.ts` 仅提供登录后可访问的附加路由（详情页、个人中心，均 `hideInMenu`）。

### 7.3 路由守卫（`router/guard.ts` `setupAccessGuard` L51-143）
1. `coreRouteNames`（Root/Authentication/BpmMobileFormPreview/404）放行；
2. 无 `accessToken` → 跳登录（带 redirect）；
3. `isAccessChecked=true` → 直接放行；
4. `dictStore.setDictCacheByApi(getSimpleDictDataList)`（不阻塞）；
5. `userInfo` 空 → `fetchUserInfo()`；
6. `generateAccess({ roles, router, routes: accessRoutes })`；
7. 写回 `setAccessMenus/setAccessRoutes/setIsAccessChecked(true)`；
8. `router.resolve(redirect)` + `replace` 重定向。

### 7.4 请求层鉴权（`api/request.ts`）
- 两实例：`requestClient`（业务，`responseReturn:'data'`、timeout 60s）；`baseRequestClient`（仅带 tenant 头，无 Authorization，用于 refresh/logout/captcha）。
- 请求拦截器：`Authorization: Bearer <token>`、`Accept-Language`、`tenant-id`/`visit-tenant-id`（`VITE_APP_TENANT_ENABLE`）、API 加解密（`isEncrypt` 时 `X-Api-Encrypt:true`）。
- 响应拦截器链：解密 → `defaultResponseInterceptor`(code===0 返回 data) → `authenticateResponseInterceptor`(401) → `errorMessageResponseInterceptor`（特判 401 静默防重复提示）。
- **401 刷新队列**（`preset-interceptors.ts` L47-110）：`isRefreshing` 为真则入队 `refreshTokenQueue` 等新 token 批量重放；否则 `doRefreshToken()`（无新 token 抛错）→ 队列回调 → 重放；失败 → `doReAuthenticate()`（modal 续登或 logout 跳登录）。

### 7.5 细粒度权限（按钮级）
- `v-access` 指令（`packages/effects/access/src/directive.ts`）：`v-access:code="['iot:device:update']"`；`mounted` 时无权限 `el.remove()`。
  - **注意**：`accessMode==='frontend' && arg==='role'` 才走 `hasAccessByRoles`，否则一律 `hasAccessByCodes`——本项目 `backend` 模式下 **`v-access:role` 形同虚设，只有 `v-access:code` 有效**。
- `useAccess`（`use-access.ts`）：`hasAccessByRoles(roles)`（与 `userStore.userRoles` 交集）、`hasAccessByCodes(codes)`（与 `accessStore.accessCodes` 交集），均为"或"逻辑（交集非空即通过）。
- `AccessControl` 组件（`access-control.vue`）：`codes` + `type`。
- `TableAction`（`components/table-action/table-action.vue`）：`action.auth` 非空时须 `hasAccessByCodes(auth)` 才渲染按钮；无 `auth` 恒显示。典型：`views/system/user/index.vue`（`system:user:create/update/delete`、`system:permission:assign-user-role`、`system:user:update-password`）。

### 7.6 前后端权限对应关系（核心原则）
- 前端 `permissions[]`（`accessCodes`）与后端 `@PreAuthorize("@ss.hasPermission('system:user:create')")` 使用**同一套字符串**。
- 前端只做 **UI 层隐藏/移除**（体验优化）；**真正的安全鉴权在后端接口**——前端隐藏按钮 ≠ 越权，后端必须对每个敏感接口独立校验。
- `roles[]` 对应后端 `@ss.hasRole/hasAnyRoles`（backend 模式前端基本不用 role 判权限）。
- `menus[]` 即页面/路由访问权限（`visible→hideInMenu`、`component→页面`、`parentId→层级`）。

## 9. 边界规则与注意事项

1. **匿名接口机制**：`@PermitAll` 启动时扫描 `RequestMappingHandlerMapping` 动态收集；`@RequestMapping` 未声明 method 视为所有 HTTP 方法免登录；另有 yaml `yudao.security.permit-all-urls`（如 `/admin-api/mp/open/**`）。新增匿名接口**需重启生效**。
2. **超管放行点（三处，注意一致性）**：`PermissionServiceImpl.java:83`（hasAnyPermissions 兜底）、`PermissionServiceImpl.java:190-192`（超管取全部菜单）、CRM `CrmPermissionUtils.isCrmAdmin()`。`RoleCodeEnum` 仅 `super_admin` 享有框架级全权限。
3. **Mock 模式风险（生产必查）**：`application-local.yaml:208`、`application-prod.yaml:195` 均设 `yudao.security.mock-enable: true`，此时 `Authorization: test<userId>` 可伪造任意用户（`TokenAuthenticationFilter.java:117-129`）。**生产环境务必置 false**。
4. **缓存一致性**：权限 Redis 缓存多为"变更即 allEntries 全清"；叠加 `SecurityFrameworkServiceImpl` 的 Guava 1 分钟二级缓存，超管降级为普通角色存在至多约 1 分钟权限滞留窗口。
5. **跨租户即跳过全部校验**：`skipPermissionCheck()` 命中（`visitTenantId != tenantId`）时，`@ss` 功能权限与 `dept_id` 数据权限**同时失效**；该能力由 `system:tenant:visit` 权限控制，需严格控制授权。
6. **数据权限只拦 ADMIN**：`DeptDataPermissionRule.java:96` `userType != ADMIN` 直接返回 null；会员端行级隔离依赖业务自身。
7. **严格模式**：`permission` 字符串未在 `system_menu` 登记（或菜单被删），即使角色曾授权也判无权限（`PermissionServiceImpl.java:95-98`）；删菜单会级联清理 `system_role_menu`。
8. **空结果保护**：数据权限条件拼不出时返回 `WHERE null = null` 保证查不到数据而非不过滤（`DeptDataPermissionRule.java:122,134`）。
9. **userType 不匹配即拒**：`login-user` header 与 Token 两条路径都比对 URL 前缀推导的 userType（ADMIN/MEMBER），不匹配抛 `AccessDeniedException("错误的用户类型")`（`TokenAuthenticationFilter.java:92-95,143-147`）——app 端 token 不能访问 admin-api。
10. **dept_id 冗余数据**：用户调岗后历史数据 `dept_id` 不洗数据会导致看不到旧数据（`DeptDataPermissionRule.java:36-45` 注释给出改造方案）；`DEPT_CUSTOM` 档已特殊保证"能看到本部门"。
11. **BPM 审批人空配置**：部署前 `validateBpmnConfig` 强校验，未配置拒绝部署；运行期候选人为空走 `ASSIGN_EMPTY` 兜底。
12. **异常语义**：未登录 → 401（`AuthenticationEntryPointImpl`）；已登录无权限 → 403（`AccessDeniedHandlerImpl`，warn 日志便于审计）；租户越权 → 403 中文提示；缺 tenant-id → 400。
13. **前端 v-access 非响应式**：仅 `mounted` 执行 `el.remove()`，不监听 `accessCodes` 变化；异步登录/切权限后需刷新或重挂组件。
14. **前端持久化边界**：`accessStore` 只持久化 token/`accessCodes`/tenant；`accessMenus/accessRoutes/isAccessChecked` 不持久化，硬刷新会重新 `fetchUserInfo` + `generateAccess`。
15. **401 不重复提示**：`errorMessageResponseInterceptor` 特判 `error.data.code===401` 静默；刷新由 `doReAuthenticate`/登录流程负责。
16. **请求实例分工**：`requestClient` 带全量头；`baseRequestClient` 仅带 tenant 头，用于 login/refresh/logout/captcha，避免 Authorization 干扰刷新死循环。
17. **API 加解密**：仅单次请求 `headers.isEncrypt` 为真时生效（登录显式关闭）；受 `VITE_APP_API_ENCRYPT_*` 控制。
18. **租户头**：`tenant-id`/`visit-tenant-id` 仅在 `VITE_APP_TENANT_ENABLE==='true'` 下发；`visit-tenant-id` 仅登录后生效。
19. **字典与权限解耦**：`useDictStore`/`use-dict` 仅提供字典缓存驱动表单/下拉，与权限码无直接关系。
