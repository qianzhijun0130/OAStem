## §0 本版修订说明（v1 错在哪）

v1 有两处硬伤，均由外部资料检索 + 实测推翻。**记录在此，避免评审时被误导。**

| # | v1 的结论 | 实际情况 |
| --- | --- | --- |
| 1 | 「生成列方案被 MySQL 否决，此路不通」（依据 `ERROR 3109: cannot refer to auto-increment column`） | **结论错误**。被否决的只是**引用自增列**的那一种写法。改用 **NULL 语义**（生成列在存活时取 1、已删时取 `NULL`，靠"唯一索引允许多个 NULL"放行已删行）即可成立，**这正是 MySQL 下替代 PostgreSQL partial index 的业界通行做法**。已实测通过（见 §5）。 |
| 2 | 推荐路径 B1：把 `is_deleted` 改为 `bigint`、存 `0 / 自身id` | **与规范冲突**。《阿里巴巴 Java 开发手册》MySQL 建表规约明确：`is_xxx` 字段必须是 `unsigned tinyint`（1=是，0=否），并直接以 `is_deleted` 为正例。把"是与否"字段改成"标识"字段，属于语义污染。 |

**修正后的推荐**：**路径 D（生成列 + NULL 语义）** —— 同时满足"数据库层保证唯一"与"`is_deleted` 语义不变"。

## §1 评审标准：企业级的 10 个可核验维度

> **说明**：不存在一份权威文件叫"企业级标准"。此处把业界共识与公开规范拆成 **10 条可独立核验的判据**——每条都给出「怎么验」，你可以逐条打勾。
> 来源标注：`[阿里手册]` 出自《阿里巴巴 Java 开发手册》MySQL 规约（经公开转载核对）；`[业界]` 出自数据库软删除实践公开文章（出处见 §9）。

| # | 维度 | 判据（怎么核验这一条） | 依据 |
| --- | --- | --- | --- |
| **V1** | 唯一性由谁保证 | 违反唯一性的**并发写入**能否被拦住？只靠应用层"先查后插"则不符合 | `[阿里手册]` 索引规约：「业务上具有唯一特性的字段…必须建成唯一索引…即使在应用层做了非常完善的校验控制，只要没有唯一索引，**根据墨菲定律，必然有脏数据产生**」 |
| **V2** | 删除后原值能否复用 | 删除一条 → 用同值重建 → 是否成功 | 「用户注销后又用同一邮箱注册」是最典型的线上投诉场景 `[业界]` |
| **V3** | 业务值是否被改写 | 查库看已删行的编码是否仍是**原值** | 审计与追溯要求；改写后**无法还原**（截断部分永久丢失） |
| **V4** | 删除标记语义是否规范 | `is_deleted` 是否仍为 `unsigned tinyint`（0/1） | `[阿里手册]` 建表规约：「表达是与否概念的字段，必须使用 `is_xxx` 的方式命名，数据类型是 `unsigned tinyint`…正例：表达逻辑删除的字段名 `is_deleted`，1 表示删除，0 表示未删除」 |
| **V5** | 是否消除"靠人记" | 新增一张表/一个删除入口时，**漏写**是否仍会被兜住 | 治理层要求：约定若不固化到结构里，就一定会被漏 |
| **V6** | 对现有代码的侵入面 | 需改动文件数、是否需回退已上线逻辑 | 变更风险控制 |
| **V7** | 可回滚性 | 有没有成文的回滚 SQL/步骤 | 运维要求 |
| **V8** | 存量数据迁移量 | 需要迁移的行数 | 迁移量随时间增长，**窗口期会关闭** |
| **V9** | 查询性能影响 | 额外索引体积、索引基数、写放大 | `[业界]` 提醒：复合索引方案有「索引碎片化、查询性能随数据量下降」的问题 |
| **V10** | 可观测性 | 该机制是否被启动自检/监控覆盖 | 治理层要求 |

### 决策规则（按数据规模分档）

`[业界]` 公开实践给出的分档建议：

- **数据量百万级以下、并发压力小** → 复合索引类方案即可，**不必过度设计**
- **高并发、强一致要求** → 放弃逻辑删除，改为物理删除 + 历史表归档
- 任何规模都成立的一条：**「删除即删除」**，用标记位长期留数据本质是**数据归档**需求，应与"删除"需求分开设计

本系统规模：核心表当前 **个位数～百行级**，属第一档。

## §2 四条候选路径

| 路径 | 做法 | 一句话 |
| --- | --- | --- |
| **A** 改写业务值 | 删除前把编码改成 `{原值}_deleted_{主键}` | **当前已落地**（`UniqueKeyReleaseUtil`） |
| **B** 复用 `is_deleted` | 列改 `bigint`，存 `0 / 自身id`，唯一索引改 `(编码, is_deleted)` | v1 曾推荐，**与规范冲突** |
| **C** 新增标记列 | 加 `deleted_flag bigint`，删除时写 `id` | 未解决"靠人记" |
| **D** 生成列 + NULL 语义 | 加**生成列** `active_flag = IF(is_deleted=0, 1, NULL)`，唯一索引改 `(编码, active_flag)` | **本版推荐** |

**路径 D 的原理**（这是 §0 里被推翻的那个"死路"）：
- 存活行 → `active_flag = 1` → 唯一索引按 `(编码, 1)` 约束 → **同编码只能有一条存活行**
- 已删行 → `active_flag = NULL` → **MySQL 唯一索引允许多个 NULL**，多条已删行互不冲突
- 等价于 PostgreSQL 的 `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`（MySQL 无 partial index，这是官方推荐的替代手法 `[业界]`）

## §4 结论与推荐

**推荐路径 D**，理由：

1. **V1 唯一性由数据库保证** —— 唯一索引始终有效，任何入口（含将来新增的）都天然安全，不依赖应用层自觉。
2. **V3/V4 两个硬约束同时满足** —— 业务值永不被改写；`is_deleted` 仍是符合手册的 `unsigned tinyint`，现有 31 处 `= 0` 存活判断、29 个测试脚本**全部不受影响**。
3. **V6 侵入面最小** —— **应用代码零改动**，实体类不动，已上线的 `UniqueKeyReleaseUtil` 可保留为历史兜底而不必回退。
4. **V8 迁移量为 0** —— 生成列不需要回填数据，存量 2 行已删记录自动得到 `active_flag = NULL`。

**已知代价（诚实列出）**：
- 需要 DDL（7 张表各加 1 列 + 重建 1 个唯一索引）
- 唯一键冲突时的报错信息变成 `Duplicate entry 'XXX-1'`（带 `-1` 后缀），用户提示文案需确认是否可接受
- 启动自检的判定口径需要同步更新（§6.3）
- 生成列对**写入**有微小开销；索引含生成列，需在压测阶段观察（当前数据量下可忽略）

## §5 实测证据

### 5.1 路径 D 的原理验证（临时表，已清理）

```sql
CREATE TABLE _tmp_gen2 (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  code VARCHAR(50) NOT NULL,
  is_deleted TINYINT NOT NULL DEFAULT 0,
  active_flag TINYINT GENERATED ALWAYS AS (IF(is_deleted = 0, 1, NULL)) VIRTUAL,
  UNIQUE KEY uk_code (code, active_flag)
) ENGINE=InnoDB;
```

| 用例 | 期望 | 实测输出 |
| --- | --- | --- |
| 插入存活 A | 成功 | ✅ |
| 再插一条存活 A | **失败** | ✅ `ERROR 1062 Duplicate entry 'A-1' for key '_tmp_gen2.uk_code'` |
| 软删 A#1 后重建 A | 成功 | ✅ |
| 反复软删/重建 3 轮 | 每轮都成功 | ✅ |
| 库内 3 条已删 A + 1 条存活 A | 互不冲突 | ✅ `active_flag`：已删=`NULL`、存活=`1` |
| 再出现两条存活 A | **失败** | ✅ `ERROR 1062 Duplicate entry 'A-1'` |

`ERROR 3109 (HY000): Generated column 'deleted_flag' cannot refer to auto-increment column.`
→ 这**只否定"引用自增列"这一种写法**，不否定生成列本身。

## §6 实施方案（路径 D）

### 6.1 DDL（逐表执行）

```sql
-- 以 oa_user 为例

-- ① 新增生成列（存活=1，已删=NULL）
ALTER TABLE oa_user
  ADD COLUMN active_flag TINYINT
      GENERATED ALWAYS AS (IF(is_deleted = 0, 1, NULL)) VIRTUAL
      COMMENT '仅供唯一索引使用：存活=1，已删=NULL（MySQL 唯一索引允许多个 NULL）';

-- ② 替换唯一索引为复合索引
ALTER TABLE oa_user DROP INDEX uk_username,
                  ADD UNIQUE KEY uk_username (username, active_flag);
```

7 张表替换对照：

| 表 | 原唯一索引 | 新的复合唯一索引 |
| --- | --- | --- |
| `oa_user` | `uk_username (username)` | `uk_username (username, active_flag)` |
| `oa_role` | `uk_role_code (role_code)` | `uk_role_code (role_code, active_flag)` |
| `oa_department` | `uk_dept_code (dept_code)` | `uk_dept_code (dept_code, active_flag)` |
| `oa_dict_type` | `uk_dict_type (dict_type)` | `uk_dict_type (dict_type, active_flag)` |
| `oa_flow_definition` | `uk_flow_code (flow_code)` | `uk_flow_code (flow_code, active_flag)` |
| `oa_company` | `uk_company_code (company_code)` | `uk_company_code (company_code, active_flag)` |
| `oa_meeting_room` | `uk_room_code (room_code)` | `uk_room_code (room_code, active_flag)` |

> ① ② 可合并为一条 `ALTER`，减少一次表重建。建议**先在一张表（如 `oa_dict_type`，数据量最小）演练**，确认应用行为正常后再推广。

### 6.2 应用代码改动

**无。** 具体说明：

| 关注点 | 是否需要改 | 原因 |
| --- | --- | --- |
| 实体类 | ❌ | `active_flag` 是生成列，实体不声明；MP 的 SQL 用显式列名，不会带上它 |
| 删除逻辑 | ❌ | `deleteById` 生成 `UPDATE ... SET is_deleted = 1`，数据库自动重算生成列 |
| 查询逻辑 | ❌ | 判断列仍是 `is_deleted`，语义未变 |
| `UniqueKeyReleaseUtil` | ❌ 可保留 | 作为历史数据兜底，不必回退；也可在观察期后删除 |
| Mapper XML | ❌ | 项目内 0 处 |

### 6.3 启动自检口径更新（`UniqueIndexReleaseChecker`）

现有口径是「**单列**唯一索引 + 有 `is_deleted` 列」。改造后唯一索引变成多列，会被现有口径排除——**这会造成"改了 DB 但自检不再覆盖"的假安全**。

需同步调整为两条判据：

1. **已适配**：唯一索引含 `active_flag`（或等价的"存活标记生成列"）→ 视为安全
2. **未适配**：单列唯一索引 + 有 `is_deleted` 列 → 仍告警（防历史遗漏/新表漏接）

### 6.4 执行顺序（每步可停）

| 阶段 | 内容 | 可停 |
| --- | --- | --- |
| 0 | 备份 7 张表（`mysqldump --single-transaction`） | — |
| 1 | 单表演练（`oa_dict_type`）+ 回归 | ✅ |
| 2 | 其余 6 张表 DDL | ✅ |
| 3 | 更新自检口径 | — |
| 4 | 回归 + 跑通 M05~M14 | — |
| 5 | 观察期后决定是否移除 `UniqueKeyReleaseUtil` | ✅ |

### 6.5 回归方案

现有 `F:/tmp/m30_techdebt_regress.py` 的断言需调整：**不再校验占位值格式**，改为直接断言「删除 200 → 同编码重建 200 → 重建后可再删」。其余（最长编码、树完整性等）保留。

## §7 回滚方案

```sql
-- 以 oa_user 为例
ALTER TABLE oa_user DROP INDEX uk_username,
                  ADD UNIQUE KEY uk_username (username);
ALTER TABLE oa_user DROP COLUMN active_flag;
```

**关键**：回滚后**必须确认没有"同编码、同时存活"的重复行**，否则新唯一索引建不上。回滚前先跑：

```sql
SELECT username, COUNT(*) c FROM oa_user WHERE is_deleted = 0 GROUP BY username HAVING c > 1;
```

数据级回滚：从阶段 0 的备份恢复。

> 路径 D 的生成列**不改变任何业务数据**，因此回滚只涉及 DDL，不需要改数据——这是它相比 B1（要改 `is_deleted` 存 id）的又一优势。

## §9 附：业界做法出处

| 来源 | 要点 |
| --- | --- |
| 《阿里巴巴 Java 开发手册》MySQL 建表规约 / 索引规约（公开转载） | `is_xxx` 必须 `unsigned tinyint`、`is_deleted` 为逻辑删除正例；有唯一特性必须建唯一索引，否则"必然有脏数据" |
| PHP Architect《Advanced Unique Index Patterns for Soft Deletes》 | PostgreSQL 用 partial index；**MySQL/MariaDB 用生成列（`IF(deleted_at IS NULL, 1, NULL)`）+ 复合唯一索引**，依赖"唯一索引允许多个 NULL" |
| ITNotes《Soft Delete Pattern in Database》 | MySQL 无 partial index；生成列是替代手法；「唯一约束需要特殊处理」是常见踩坑点 |
| Let's Build《Designing a Soft-Delete and Data Lifecycle System》 | 「唯一约束与软删除的结合点，是大多数实现出问题的地方」；独立 tombstone 表的取舍 |
| CODERCOPS《Soft Delete vs Hard Delete》 | 唯一约束在软删除下"按字面写是不工作的"，需要 partial index 或把删除标记并入唯一键 |
| TrueSight《逻辑删除的幻象》 | 方案优缺点对比；**百万级以下不必过度设计**；「删除即删除」，标记位留数据本质是归档需求 |

> 注：阿里手册条款引自公开转载版本；生成列手法引自多个独立的数据库实践文章，彼此结论一致。实际落地前建议在目标 MySQL 版本上按 §5.1 复验。
